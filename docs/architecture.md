# Provisional Architecture

**Current implementation — authenticated Immich photo browsing, Home-aware Stack organization, Anshitsu, Recipe v18 JPEG adjustments, History, persistent edit state and Export Queue are implemented. Production Export uploads JPEGs, assigns the GenzoRoom tag, registers the generated output in the source Stack and makes it the Cover, with serial runtime and Stop/Retry/restart recovery. NAS/Immich Export verification and Home-time silent tag-repair verification have been completed. RAW development remains unimplemented.**

This document describes the current implementation and possible future extensions. The architecture remains provisional: components, interfaces, and deployment choices may change during development.

## Current request flow

Gallery-to-Develop navigation (Phase 3) sends each selected Stack's complete Phase 2 target list through `workspaceAssetResolver.ts` into the existing `createWorkspaceNavigation()` contract. All four tabs, including Favorites, use the same target rules; favorite membership controls cards, not the Stack's child candidates. Card selection order and the original Stack member order are retained, with case-insensitive Asset ID deduplication at the first occurrence. An unavailable Stack aborts the whole operation; a ready empty Stack contributes no assets, and an overall empty target list shows a distinct message without resuming the last workspace. The separate zero-card-selection branch still resumes `readWorkspaceSession()` exactly as remembered and refreshes only `homeReturn`. A synchronous navigation guard blocks duplicate successful route requests. Anshitsu's save, switch, Home exit, Filmstrip, and resume ownership remain in the existing components.

Gallery Stack format switches (Phase 4) are sibling controls of the PhotoCard body button. `StackFormatSwitches` derives each format/is_raw group's pressed state from the Phase 2 selection IDs, never from the preset directly. Activation removes all eligible members of an ON group or adds all members of an OFF group, preserving other groups through the existing manual-selection store. No separate badge state or persistence exists. A complete snapshot reconciles stored intent in an effect rather than publishing during render, and only when the shared request-generation guard identifies it as current; an older tab cache cannot prune newer IDs. Export-only groups are disabled and OFF; unavailable snapshots disable every group, omit aria-pressed and expose the unavailable explanation. Card selection, range anchors, Queue and navigation remain independent.

Gallery Stack candidate metadata (Phase 1) lives in optional `RecentAsset.stackMembers`, using the same `RecentAsset` member model as `ImmichStack.assets`. Backend attaches complete IMAGE members from the same `/stacks` snapshot used for display membership and formats; it never resolves individual cards. Missing member details or unknown export tags omit this field while preserving the existing Gallery display. Tag lookup uses exact Immich `GenzoRoom` relations, combining unknown cover/member IDs into deduplicated bounded batches; cover identity is never inherited by children. After tag resolution, the backend compares definite tag evidence for duplicate asset IDs across the Home result and attached member list. A conflict makes only that Stack's `stackMembers` unavailable while preserving its Home card and representative tag; unknown evidence remains unknown and never becomes a guessed false value. Frontend validates membership, primary, count and per-member boolean tag state atomically at the API boundary, and rejects candidate metadata if the representative's definite tag differs from its Primary member. Each Gallery tab retains its display data in its existing response-owned asset array, while `useGalleryStackSelections.ts` owns one in-memory current candidate snapshot per Stack ID for the mounted Gallery page. Asset-list requests receive a monotonic generation at request start; an accepted response replaces a Stack snapshot only if its generation is not older than the currently registered one. Selection controls and Develop resolution use that shared snapshot even when a tab displays older cached card data. Each request is tracked until acceptance, failure or cancellation. Destructive session reconciliation uses the newest accepted snapshot for that Stack and is deferred only while a newer request remains unresolved; completed unrelated requests do not block it. Finishing a pending request publishes the shared store revision so visible format controls retry reconciliation without a snapshot change. Older responses and temporarily unavailable snapshots preserve manual intent. The request/session generation is in-memory only, does not change the `sessionStorage` format, and the Gallery candidate snapshot cache is cleared when the page unmounts. `galleryStacksById()` still derives a Stack-ID lookup from an asset response without per-Stack requests. A missing member list means unavailable and must block candidate selection, not mean no candidates. Phase 1 does not change selection, badges, Queue, Favorites semantics or workspace resolution.

Gallery Stack context actions (Phase 5) live in a body portal opened by the card's contextmenu event; the photo body and format switches keep their click behavior. The upper section uses the validated full Stack snapshot in member order, excludes exported Assets, and reads/writes the same manual Asset ID set used by format switches and Develop navigation. The lower section derives candidates independently from per-Asset Recipe edit status and includes existing Queue entries so removal stays possible when edit state is unknown. Queue membership and processing locks come from `useExportQueue()`; member mutations reserve the same Asset IDs as card and batch actions. Queue failures use the existing error surface and request a refresh. Unknown member, edit, or Queue state is shown separately from an empty candidate list; the menu adds no persisted state. The fixed portal clamps its measured bounds to the viewport from the original pointer coordinate, remeasuring after content-size or window-size changes; the bounded menu scrolls when its rows exceed the available viewport. Initial focus runs once after measured placement commits a visible menu, targeting the first enabled checkbox in the upper then lower section, or the menu itself. Later reflows and asynchronous updates preserve active focus; a removed or disabled focused checkbox retreats to the menu even when the disabled input remains the active element, while another enabled control retains its focus.

Gallery-to-Develop target selection (Phase 2) is a pure function in `galleryAssetSelection.ts`, including an entry point that consumes the Phase 1 `galleryStacksById()` index. For a Stack card it requires a complete, internally consistent member list and a definite export-tag boolean per member; the result distinguishes unavailable data (`assets: null`) from an available empty target list. Stack presets select every unexported asset of the requested type, with type fallback only for the initial preset. A standalone card resolves directly to itself. `useGalleryStackSelections.ts` owns only manual overrides in `sessionStorage`, keyed by Stack ID, with an explicit empty array representing a manual all-off choice. Only a complete current member snapshot can reconcile stored IDs; unavailable snapshots leave stored intent untouched, while removed/exported members are pruned and new members are not added. General settings persist `anshitsuInitialSelection` in localStorage and currently accept only `nonRaw`; the `raw` and `both` values remain in the type for later enablement and their controls are disabled while RAW development is unavailable. Phase 2 exposes this selection infrastructure without connecting it to workspace navigation or changing Gallery badge actions.

React Home has four browsing tabs: Recent, Albums, Calendar, and Favorites, plus an Export management tab. Its page is a Header / Tabs / Toolbar / Content shell: Header, Tabs, and Toolbar remain outside the `.home-content` scroll container, and only `.home-content` scrolls. The former large photo-area enclosure is removed. Home and STACK management share neutral dark semantic tokens; Developer Diagnostics retains its green console identity, and Anshitsu keeps its separate theme. Recent requests 50–500 Timeline images in steps of 50 (100 by default); Favorites requests favorited Timeline images; Albums lists collections and loads assets when a collection is opened. Calendar has year, month, and date-detail views. Its availability and minimum year use Timeline IMAGE assets so Archive-only or video-only dates are not marked as photo days; month thumbnails use the first eligible non-RAW IMAGE in Timeline order. In every Calendar view, unmodified Left / Right move backward / forward on the time axis: month view changes month (including year boundaries), year view changes year while retaining the month, and date detail moves between days containing photos. Calendar navigation is centered in the Home Toolbar rather than sticky inside the content scroll region.

Home metadata searches exclude trashed assets with `trashedAt: {eq: null}`. Recent, Favorites, Album assets, and Calendar date assets then join against Immich's Stack snapshot. Calendar month/year presence uses `/timeline/bucket`; its `fileCreatedAt` plus `localOffsetHours` determines each local day. Date detail reuses `_calendar_month_images()` for that same local-day decision, extracts only IDs for the selected day, and deduplicates them while preserving timeline order. It fetches metadata in batches of 100, maps results by ID, and restores timeline order independently of metadata search order. An empty day skips metadata search. The results then pass through the existing Home Stack join, retaining primary-only cards, Stack metadata, and quarantine of malformed, ambiguous, or missing-primary members. Timeline failures do not fall back to the former UTC `takenAt` range search. The frontend `/calendar/{date}/assets` contract is unchanged. Home parsing is deliberately non-fatal: malformed entries, duplicate Stack IDs, duplicate members, ambiguous ownership, and invalid membership are quarantined. Their member IDs and possible primary IDs are not returned as ordinary photos, because an incomplete snapshot must not turn surviving children into apparently unstacked cards. A valid Stack contributes only its primary to the Home result; the primary retains `stackId`, `primaryAssetId`, `stackAssetCount`, and `stackMemberIds`. Recent fetches further cursor pages when filtering leaves fewer than the requested visible count, and validates cursor progress before using each page. Album searches keep their existing visibility semantics and do not add a Timeline-only restriction, so Archive assets in albums remain eligible.

Recent, Favorites, Album details, and Calendar date details use one shared photo-card grid with independent per-tab RAW / Non-RAW and edited / unedited filters, adjustable thumbnail size, edited and format badges, and ordered multi-selection with Shift+click ranges. Recent, Album, and Calendar photo views filter stacked versus unstacked cards; the backend has already reduced each valid Stack to its primary photo. Favorites also receives primary-only Stack data but does not apply the stacked/unstacked filter or collapse step. `stackMemberIds` on a primary lets edit-status lookup include all known Stack members; a Stack is filtered as edited if any known member is edited, and as unedited only when every member's status is known and none is edited. When a view returns only part of a Stack, missing member state remains unknown rather than being treated as unedited. Each photo view has its own selection state. `photoView` in `GalleryPage.tsx` resolves the active photo grid's assets, load state, selection, and edit-status inputs; Album lists and Calendar year/month views have no active photo view. `usePhotoSelection()` owns one view's selected IDs and range anchor while GalleryPage keeps one instance per photo view. A normal click selects only that photo; Primary+click toggles it, and Shift+click adds the inclusive range from the anchor. A first Shift without an anchor is a no-op. Checkboxes toggle or extend the range with Shift, while Clear/Escape clears selection. Anshitsu entry remains the selection toolbar or D; the P command and double-click entry are prepared boundaries for future Preview, whose UI is not implemented. Select All adds only `visibleAssets` to the existing selection, preserving hidden IDs and selection order. The compact Selection group appears only for photo views. Tab-specific filters use session storage; thumbnail size uses browser-saved Settings. Home passes the ordered concrete asset selection directly to `/stack`; the `S` command is available only when a selection exists and remains separate from the Anshitsu `D` command.

The Home Stack parser and the Stack-management resolver have different safety goals. Home uses valid metadata when available and quarantines uncertain ownership to keep browsing available without exposing possibly stacked children. Stack management uses strict resolution and does not permit ambiguous or incomplete snapshots to enter an editable draft. This browsing fallback does not weaken Stack ownership validation or write preconditions.

For Home, the backend builds optional Stack display metadata from the full Immich Stack snapshot, then returns only the primary/Cover as the photo card. The primary carries `stackMemberIds`, `stackAssetCount`, and `stackFormats`; `stackFormats` is the unique `(format, isRaw)` sequence with the primary format first. Malformed optional format metadata is ignored without dropping an otherwise valid asset. The frontend sanitizes optional metadata again before rendering. Stack format badges are informational and do not change which asset is selected or shown as the card.

`FilenameDisplay` is shared by `PhotoCard` and `ExportManagement`. It keeps the full filename in its title/accessibility label and uses a flex layout where the prefix can ellipsize while the extension and a bounded trailing identifying segment remain visible. It changes display only; the underlying filename used by selection, search, and export is unchanged.

Home enriches assets with the backend's GenzoRoom tag state (`present`, `absent`, or `unknown`) and exposes the display-only `isGenzoRoomExport` boolean to `PhotoCard`, which renders `GenzoRoomExportBadge`. The state is for the Cover/primary asset itself; child tags are not aggregated. Unknown is not treated as absent and cannot enter repair.

For Recent, Favorites, Album detail, and Calendar day detail, Home returns its response before dispatching best-effort background tag repair. Candidate collection visits each Home representative first, followed by its `stackMembers` in member order; each asset is evaluated independently using its own `isGenzoRoomExport` and filename, and Asset IDs are deduplicated without inheriting Cover tag state. Null or empty `stackMembers` are valid. Repair considers only tag-absent candidates and requires an exact GenzoRoom output filename plus JPEG EXIF Software exactly equal to `GenzoRoom`; these verification conditions are unchanged. Candidate originals are fetched sequentially, only as needed, with a 64 MiB cap; pending work is bounded to 128 and in-flight work is deduplicated. A bounded 512-entry negative cache stores only valid JPEG `NO_MATCH` results. Missing tags are assigned through the same Immich tag-assignment helper used by Export. Repair remains best-effort and non-blocking for Home.

JPEG marker analysis returns `MATCH`, `NO_MATCH`, or `INVALID`. `MATCH` requires a structurally plausible JPEG container and exact EXIF Software identity; `NO_MATCH` is reserved for a valid container and valid or absent EXIF identity that does not match. Malformed EXIF, invalid marker/container structure, original fetch/size/length failures, and temporary write/API failures are not negative-cached, so a later Home visit can retry. Structural validation checks JPEG marker and segment bounds, required tables, SOF/SOS/EOI structure, EXIF TIFF header and IFD boundaries, and Software field type without pixel decode. XMP-only identity is not sufficient. Repair is best-effort and silent; Export registration remains fail-fast.

Export registration and repair use the shared GenzoRoom tag-assignment helper for tag upsert, asset assignment, response validation, and Asset detail confirmation when Immich reports zero assigned assets. The helper is shared, but failure policy is operation-specific: Export fails fast when required registration is incomplete, while Home repair logs a recoverable failure and continues browsing.

Home keeps in-memory scroll offsets by view: Recent, Favorites, Album list and each Album ID, and Calendar year, month, and date. On Anshitsu or STACK navigation, Home passes its tab, detail context, calendar mode, and page/content scroll coordinates in route state; the route validates that context and restores after the required view data is ready. When route exit occurs during restoration, `captureHomeReturn()` uses the pending offset only if its key matches the current view, so a loading DOM position cannot replace the intended scroll position. Ordinary tab navigation uses the same view keys and pending restoration mechanism. Album-detail and Calendar-date selections remain available when switching tabs; reactivating their already-active tab returns to the parent view. These rules remain coordinated in GalleryPage rather than being spread across data hooks.

The Home Toolbar adapts by width without changing view ownership: Recent and Favorites place Selection at left and filters/display controls at right; Album lists keep thumbnail sizing at right; Album and Calendar date details use a centered three-column title on wide screens, move the title to its own row at the `76rem` breakpoint, then stack regions at 760px and below. Calendar year/month navigation remains centered in its own Toolbar layout. Selection groups retain their intrinsic width so localized labels and shortcut suffixes remain operable.

Calendar date details place previous/next photo-day buttons around the centered date title. `useAdjacentCalendarDates` owns their asynchronous candidates and successful year-heatmap cache for the mounted Home session. Only `hasAssets === true` dates qualify; searches share in-flight year requests and stop at the Calendar minimum/current year. Date changes, leaving detail, tab switches, and unmount abort the active search; inactive responses cannot publish candidates or populate the cache. Month and year arrow keys reuse `adjacentCalendarPeriod` and `changeCalendarPeriod`, preserving the button boundaries and scroll ownership. Date-detail buttons and arrow keys share the adjacent-day navigation path, which calls `openCalendarDay` to clear the old selection, invalidate asset requests, transition scroll, and synchronize date/year/month while retaining the parent mode. HomeReturn keeps its existing shape. Keyboard handlers respect modifier, repeat, IME, native editing, and open dialog/menu guards; boundary moves remain unconsumed. Disabled date-detail arrows use the default cursor. Home tabs use ordinary button tab stops; Arrow/Home/End no longer change tabs, while R/A/C/F and click navigation remain available.

### Stack management drafts

Home mounts Stack management as its `Stacks` / `STACK管理` tab, passing the ordered concrete selection, including RAW and Favorites assets, directly and bypassing the Anshitsu workspace asset resolver. The old `/stack` route redirects to Home. Tab entry compares unique asset ID sets: an empty selection or the same set (including reordered selections) retains the previous session; a different nonempty set remounts the editor without confirmation. First entry without selection displays an empty editor. Switching Home tabs preserves draft edits, Undo, local selection and editor scroll; changing Gallery selection alone does not alter the draft. Replacement clears all editor state, and unmount cleanup aborts and invalidates loaders and the send wait so late results cannot affect the new session. The Develop / 暗室へ button lives after the management tabs and shares the existing D navigation path; Anshitsu remains a separate workspace route. Automatic detection creates local draft Stack groups and does not modify Immich. An asset with `stackId != null` is excluded from candidate detection. NAME candidates require at least two assets in the same case-sensitive filename family, regardless of format. The family is the root before the first dot, with a terminal `-Genzo[0-9]+` output suffix removed; invalid or empty roots are ignored. NAME candidates take priority and survive missing, mismatching, or failed EXIF evidence. Remaining non-Stack assets form format-independent fallback groups of two or more members when TIME and CAM match and all available GPS positions are within tolerance. Missing GPS is allowed; malformed GPS, missing required TIME/CAM, and detail failures exclude the affected asset from fallback. Assets enter the first compatible group in Home selection order, with each addition checked against the entire group to prevent tolerance chains. Group and member order follow selection order, and every unique asset ID belongs to at most one candidate. A fallback group reports NAME as mismatch with reason `exif-fallback`; NAME family groups use `filename-family`.

Asset details are requested for NAME candidate members and, when the remaining non-Stack selection contains at least two assets, those remaining assets that could participate in fallback matching. Existing Immich Stack assets are never requested. The hook uses at most four concurrent requests per generation. Re-detection aborts the previous generation; cleanup aborts on unmount, and generation checks prevent stale responses from replacing current evidence. Partial detail failures retain NAME candidates and prevent failed members from entering fallback groups.

NAME, TIME, CAM, and GPS evidence each use four states: `matched` (green), `mismatch` (yellow), `unavailable` (dark and inactive), and `error` (red). A mismatch means values were evaluated and differed; it is not an operational failure. Fallback NAME mismatch is explained as a filename-family mismatch. Missing information such as absent GPS is unavailable, while failed detail retrieval or unusable present values are errors. TIME compares EXIF `date_time_original`: when every member has a valid value, a maximum spread of two seconds is matched and a larger spread is mismatch; missing data is unavailable. CAM requires both make and model for every member and compares the pair case-insensitively; missing fields are unavailable. NAME GPS evidence requires valid latitude and longitude for every member; missing GPS is unavailable. Fallback GPS evidence compares only members with complete positions and is unavailable when fewer than two positions exist. Both use a maximum latitude and longitude spread of `1e-5`; any malformed coordinate is an error. Backend Asset detail exposes latitude and longitude as optional EXIF fields, preserving compatibility when they are absent.

The automatic COVER is selected from `RecentAsset.date`, preferring the latest JPEG, then the latest Non-RAW asset if no JPEG exists, then the latest member if there is no Non-RAW asset. Valid dates take precedence over unavailable dates; ties preserve Home selection order.

Selected existing Immich Stacks are resolved by the Frontend in sequential, deduplicated chunks of at most 100 UUIDs per read-only `POST /stacks/resolve`; the Backend's per-request limit remains 100. All chunks share one AbortSignal, each response is strictly validated against its requested IDs, and results return in the original deduplicated request order. Any HTTP, parse, or validation failure rejects the complete resolve rather than returning partial groups. Stack management requires unique, well-formed membership and a primary present among the members; requested stacks must contain at least one complete IMAGE asset. A one-member snapshot is preserved as an abnormal singleton source rather than treated as a normal editable Stack. Unknown requested IDs, malformed members, ambiguous ownership, and upstream errors fail the whole resolution. Full members carry identical Stack ID, primary ID, and member-count metadata. `useSelectedImmichStacks` owns abort, generation checks, failure status and retry. Full membership is resolved before auto-detection inputs are formed, so even a selected asset with stale non-Stack metadata cannot appear both in an Immich group and an auto group.

An imported draft has `origin: immich`, a distinct `draft:immich:` UI ID, `immichStackId`, `originalPrimaryAssetId`, and immutable `originalMemberIds`. Its initial COVER is the upstream primary, and upstream member order is preserved. Immich group modified state compares the current unique member ID set (ignoring order) and COVER against the immutable original member IDs and primary. Exact restoration clears modified and returns the translated IMMICH indicator to green; remaining differences show yellow. After each editing action, a non-Immich group with an exact original member set regains the missing Immich lineage only when one snapshot matches and that lineage has no active owner. Partial/superset matches, duplicate IDs and ambiguous snapshots do not restore lineage. Its local UI ID and current COVER remain unchanged. Existing Add/Purge/manual-creation operations remain local. Group Purge or dissolution below two members removes the editable group but retains its original state in `sourceGroups`, allowing later unchanged/update/delete/create classification. Re-detection refreshes both membership and auto detection, with the existing confirmation on modified drafts. Editing starts only after resolution and detection complete; resolve errors block editing and never expose selected representatives as ordinary unmatched assets. Editing remains local until the user confirms Send to Immich.

An Immich singleton is abnormal when its source group has `origin: immich` and exactly one original member. It remains visible with warning styling and accessible warning text, but the member cannot be added to, moved, dragged, or used for COVER changes. Only Purge of the whole group is enabled. Purge removes it from the current draft while retaining its source snapshot, so the existing write-plan builder classifies it as one DELETE; no special write path is used. An untouched singleton is excluded from operations and from normal unchanged completion, remains in the candidate view, and causes no Immich request. If a send plan has zero operations, the UI reports “No changes to apply” / “変更はありません。” rather than success.

The header and control bar stay outside the content scroll container. The toolbar shows a shared write-plan summary of pending create / update / delete counts only when at least one operation exists. Individual delete-pending rows are not rendered; send outcome status is shown beside the STACK candidates heading, while load, detection, API, and send-limit statuses remain in the content area. The confirmation dialog uses the same plan counts. Re-detection reads the existing detail API; optional malformed GPS is omitted without failing the photo. Refresh sends distinct selected asset IDs in sequential chunks of at most 1,000 with one AbortSignal, then validates the combined result; identical full Stacks repeated across chunk boundaries are deduplicated, while conflicting copies or duplicated membership fail the whole refresh. Manual draft group creation, Purge, Add, and COVER changes are local only. Modified drafts require a Cancel-first confirmation dialog before re-detection. Stack Add uses the registered unmodified A command; Escape is local page dismissal. Both follow the page shortcut guards. Native desktop Drag & Drop uses explicit draft actions: unmatched to group is Add, member to group is one atomic move, member to unmatched section or photo is Purge, dropping one unmatched photo onto another creates a two-member MANUAL Stack in one atomic edit, and unmatched photos dropped on empty section space are a no-op. Only a valid unmatched-photo target consumes its drop; Stack-member drops bubble to the section Purge handler. These actions do not reorder groups/members or change COVER except for the new group's automatic COVER selection; send classification still uses the final draft state. STACK management supports one-step local Undo with `Primary+Z` and intentionally has no Redo. Draft persistence remains unimplemented.

For browser D&D compatibility, thumbnail images are `draggable=false`; their enclosing photo buttons are the internal drag sources. A custom MIME payload (`application/x-genzoroom-stack-photo+json`) carries the asset and source group. The active payload is also held in a ref so dragover can fall back synchronously only when the internal custom MIME type is present, has no readable data, and the transfer contains no files. Drag feedback uses a transparent native helper to suppress the browser's native ghost and a separate photo-only DOM preview sized to the rendered thumbnail. The custom preview follows the pointer using the initial thumbnail grab offset and uses 0.88 opacity. Valid group, unmatched-area, and unmatched-photo drops continue through their existing target handlers; singleton sources and targets remain rejected.

While the Stack page is mounted, window and document capture listeners observe active internal `dragover` / `drop` events for `stack.dnd` diagnostics only. They do not call `preventDefault`, stop propagation, change draft state, or affect drop acceptance. Existing React target handlers suppress the browser default only for valid targets and perform the corresponding operation. The global observer records `defaultPreventedBefore`, `defaultPrevented`, `cancelable`, listener scope, event phase, target kind/tag, and safe DataTransfer metadata; bounded dragover samples are deduplicated during the session.

DEBUG diagnostics correlate `dragstart`, global and target `dragover`, accepted/rejected drop results, and `dragend` with a `dragSessionId`. Drop results carry `accepted` and `rejectionReason`; `dragend` instead records DataTransfer types/state, `effectAllowed`, `dropEffect`, target, coordinates, buttons, modifiers, cancellation state, and payload presence. It does not claim a drop acceptance result. There is no incident-specific post-drag observer or timer. The reported Firefox new-tab behavior was traced on-device to the `fire-drag` extension, so the temporary global default suppression was removed; this extension-related incident is not treated as a GenzoRoom D&D defect.

### Stack write workflow

`buildStackWritePlan` classifies current editable groups against uncompleted immutable source snapshots, using unique member ID sets and primary equality rather than edit history or indicator classes. Existing identical Stacks are unchanged (no API call); changed Immich groups are updates; missing Immich lineages are deletes; auto/manual groups are creates. A native confirmation dialog shows create/update/dissolve counts, focuses Cancel and isolates shortcuts. Sending disables draft editing and re-detection; a synchronous request ref prevents double submission. Home navigation remains available. Unmount aborts only the frontend wait, without retrying or assuming that upstream writes stopped.

Backend `POST /stacks/apply` accepts explicit correlated operations. Validation forbids extra fields, invalid UUIDs, fewer than two or duplicate final members, non-member primaries, duplicate operation IDs, conflicting Stack operations and shared assets across final create/update memberships. Limits are 500 operations and 1,000 members per operation; empty requests do no upstream I/O. The frontend exposes the same limits before sending. Backend operation IDs are capped at 200 characters; long filename-derived draft IDs are mapped to unique bounded per-plan operation IDs and results are mapped back to their local group IDs.

The contract is verified against Immich v3.2.4 [Stack DTOs](https://github.com/immich-app/immich/blob/v3.2.4/server/src/dtos/stack.dto.ts), [controller](https://github.com/immich-app/immich/blob/v3.2.4/server/src/controllers/stack.controller.ts) and [repository](https://github.com/immich-app/immich/blob/v3.2.4/server/src/repositories/stack.repository.ts). POST `/api/stacks` accepts `assetIds`, with COVER first, and returns 201 with a Stack. PUT `/api/stacks/{id}` accepts only `primaryAssetId`, returning 200 with a Stack; membership changes therefore release the old Stack through DELETE and create its replacement with a new ID. DELETE returns 204. Successful create/update responses require valid Stack/member IDs, unique matching member sets and the requested primary, independently of response ordering. Malformed success responses are outcome unknown, not safe-to-retry failures.

The executor preloads current upstream membership and rejects missing update/delete targets. All deletes and membership-changing update releases occur before final PUT/POST calls, including membership cycles. Because Immich create can merge entire Stacks when including their primaries, any final operation with members still owned by an unreleased Stack is blocked. Independent operations continue. There is no automatic retry, rollback, cross-call transaction or invented revision lock; concurrent upstream changes after the preflight read remain possible. Client URL construction, API-key headers, timeouts, `trust_env=False`, redirect refusal and sanitized errors follow the existing boundary.

Results distinguish success, failed, unknown and blocked per operation. `releasedStackId` records a committed delete even if replacement fails. The reducer's result action removes successful/unchanged groups without returning their members to unmatched; unrelated unmatched and unused released members stay available for further editing. Write-result evidence remains on candidate groups. Send-level success, no-change, failure, and unknown status is displayed beside the candidate heading, not as an individual delete row. Failed/blocked groups have red accessible status indicators and may be explicitly resent. Unknown results also remain visible, explicitly describe uncertainty and block all sends until re-detection. A lost/malformed backend response conservatively marks outstanding operations unknown. Every send is bound to the current router navigation/source generation; changing location state aborts its request, and stale completions cannot update the new draft, status or sending state. Unchanged local completion is deferred until the same generation check.

The backend Immich HTTP client uses a 5-second read timeout (3-second connect timeout). A maximal batch can perform one Stack preflight and, for each of 500 operations, a release plus replacement write: up to 1,001 sequential Immich requests. The exact nginx `/api/stacks/apply` location therefore uses a 90-minute read timeout, calculated from 1,001 × 5 seconds (about 83 minutes 25 seconds) with processing margin. The exact `/api/developer/export-engine`, `/decode`, and `/roundtrip` POST locations use a 1-hour proxy read timeout as a safety ceiling for in-process diagnostics; their frontend manual Cancel/Abort remains the normal stop control. All other `/api/` routes retain their 10-second proxy timeout. These proxy limits do not change the backend Immich network timeout, response buffering, or Stack unknown-result handling. Transport outcomes that cannot be confirmed remain unknown, create is never automatically retried, replacement keeps `releasedStackId`, dependent operations remain blocked, re-detection is required, and no rollback is attempted.

| State | Owner | Meaning and invariant |
| --- | --- | --- |
| `completedSourceIds` | Editable draft reducer | Retires confirmed or successfully applied source work while preserving the original `sourceGroups` array identity. Retired snapshots cannot regenerate deletes or restore old lineage. A replaced restored group can retain its local UI ID independently of its original snapshot ID. |
| `writeResults` | Editable draft reducer | Correlated per-operation status; delete failures remain retryable even without a current group. A committed replacement release converts remaining work to MANUAL/create, so retry does not repeat deletion of the old Stack. Unknown outcomes survive local editing until reset/re-detection. |
| Send controller/ref and status | Stack page | One active request, localized live status, no request loop or background queue. Requests capture the confirmed plan; editing is disabled until results are applied. |

User-triggered re-detection calls read-only `POST /stacks/refresh` with the original selected asset IDs, split into sequential chunks of at most 1,000, rather than stale route Stack IDs. It resolves current full membership after create/delete/replacement, removes stale selected Stack metadata from auto inputs and rebuilds the source after all chunks and both loaders complete. Identical full Stacks repeated across chunk boundaries are deduplicated; conflicting copies or member ownership fail the entire refresh. The shared AbortSignal and hook generation reject partial, aborted, or stale results, and the current draft is retained until refresh succeeds. Sending never changes route/Home selection, auto-re-detects, resets the page or navigates away. Draft persistence is not added; the transient one-step local Undo is described above and never rewinds Immich writes or results.

### Keyboard command architecture

`frontend/src/editShortcuts.ts` is the central registry for application command bindings. Its `shortcutBindings` registry maps the `ShortcutId` union to declarative key/code and modifier definitions. `matchesShortcut()` matches a command including its modifiers; `matchesShortcutKey()` matches the physical/logical key without requiring the original modifiers, as needed for release handling. The registry owns command identity and binding matching, while Home, Anshitsu, ImageViewer, Filmstrip, ScopePanel, and other feature owners keep their own listeners, action execution, availability, and state. GenzoRoom does not use a monolithic global shortcut dispatcher.

`frontend/src/shortcutModifiers.ts` resolves logical Primary and Alternate modifiers for the current platform and provides the shared Primary-modifier check for modified pointer actions. Primary is Ctrl on Windows/Linux and Command on macOS; Alternate is Alt on Windows/Linux and Option on macOS. Registry matching and display formatting use this same resolution. Bindings that require a physical Ctrl, Meta, or Alt remain explicit exceptions; a logical Primary binding rejects the opposite physical modifier rather than accepting Ctrl+Meta together. AltGraph remains excluded where required.

Callers apply the guards appropriate to their command, such as already handled events, IME composition, repeated keys, native editing targets, open dialogs or menus, and disabled, blocked, switching, or saving states. Native and local UI behavior—Tab navigation, Escape, Enter / Space, slider arrows, component focus navigation, and native form editing—is separate from application commands.

`frontend/src/shortcutDisplay.ts` formats human-readable labels from `shortcutBindings`; components do not maintain a second copy of binding strings. It formats arrows, physical Backslash, and Numpad codes (including Numpad `-` / `+`) for display, and shows multiple bindings such as Redo together. Primary displays as Ctrl on other platforms and ⌘ on macOS; Alternate displays as Alt and ⌥ respectively. Shift matching uses the same `shiftKey` semantics on every platform, while its label is Shift on other platforms and ⇧ on macOS. This is a display-only difference and does not change matching. Explicitly physical modifier bindings retain their physical labels. `useShortcutDisplay.ts` applies the `showKeyboardShortcuts` preference to Tooltip and Menu explanations without changing command matching or action availability. Tooltips retain their normal description when shortcut labels are off, and Menu items remain present without their shortcut labels. Tooltips distinguish held Before from the persistent Before / After button and describe Shift+Z (⇧+Z on macOS) as a Fit / previous-transform toggle rather than the Fit button action.

Current commands include Home `R` / `A` / `C` / `F` / `E` for browsing/Export tab navigation, `S` for STACK management, `D` for opening a selection or resuming the last Anshitsu workspace, and `Primary+A` for Select All in photo views or mutable Export cards. Export additionally uses unmodified `W` for readiness and `Q` for removal; Gallery/Anshitsu `Q` keeps its Queue-toggle semantics. The `calendarNavigatePrevious` / `calendarNavigateNext` registry commands bind unmodified ArrowLeft / ArrowRight for Calendar previous / next time navigation; they apply only to Calendar, while native inputs and boundary states retain their key behavior. Home tabs use ordinary Tab stops and do not switch with ArrowLeft / ArrowRight / Home / End. Anshitsu / STACK return to Gallery uses unmodified `G` through the existing save-and-return flow where applicable. Anshitsu `F` toggles Viewer focus mode without changing panel state, and `Shift+Z` (displayed as ⇧+Z on macOS) toggles Fit and the previous zoom/pan transform. Filmstrip asset movement uses Primary+Shift+ArrowLeft / Primary+Shift+ArrowRight as a workspace command independent of hover or focus (⌘+⇧+←/→ on macOS). Viewer `]` toggles Preview / Original, and physical Backslash holds Before; the `]` comparison is checked first for JIS keyboard events that can match both. Undo / Redo use Primary+Z, Primary+Shift+Z, and Primary+Y (⌘+Z, ⌘+⇧+Z, ⌘+Y on macOS). Edit-settings copy/paste uses Primary+C / Primary+V, with Primary+Alternate+C / Primary+Alternate+V for selected values. Scope uses Numpad 1–3 for RGB, Numpad 0 for Y Only, and Numpad Decimal for scale; these are physical `code` bindings, not top-row digits or Period. The shared `HomeThumbnailSizeControl` used by Gallery/Home, Export management, and STACK management binds NumpadSubtract / NumpadAdd by `KeyboardEvent.code` to the same bounded decrease / increase callbacks as its buttons; ordinary Minus / Equal keys are not bound.

The thumbnail-size listener follows the shared application guards for processed events, IME composition, repeat, native editing targets (including the focused range control), and open dialogs or menus. This command is owned by the shared controller, so page consumers do not duplicate key handling.

Anshitsu navigation resume is held only in a module-level in-memory store for the current SPA session; it uses no Storage API and is lost on reload. When the app actually returns to Home, Anshitsu records the valid `WorkspaceNavigationState`: `selectedAssets` in Filmstrip order, current `activeAssetId`, and the Home return context. On Home, a current selection always takes priority for `D`; otherwise `D` resumes that workspace and replaces its `homeReturn` with the current Home context. The store does not retain Recipe, History, Viewer transform, or other transient Viewer and panel state.

Anshitsu derives one workspace keyboard-availability state from Settings, open dialogs and menus, switching, exit saving, and failed switch or exit saves. G / F, Viewer, Filmstrip, Scope, and the `useAssetEdits` Undo / Redo listener receive the relevant blocked state from the workspace owner. In particular, a save-failure alertdialog blocks Undo / Redo so it cannot change the Recipe or History behind the dialog; closing the dialog restores normal shortcut handling.

The backend exposes `/assets/recent`, `/assets/favorites`, `/albums`, `/albums/{id}/assets`, `/calendar/heatmap`, `/calendar/min-year`, and `/calendar/{date}/assets` for Home browsing. Immich credentials and upstream requests remain backend-only. `/assets/edit-status` batches edit-status reads, while `/assets/{id}/edit-state` reads and writes GenzoRoom edit state in SQLite. Album asset visibility follows the existing album search behavior; Timeline visibility filters apply to Recent, Favorites, and Calendar. The shared grid opens selected photos in Anshitsu. The desktop workspace keeps History and EXIF in the independently collapsible left reference panel, places Scope above Develop controls in the independently collapsible right panel, and extends the right panel to the bottom edge. The Filmstrip occupies the lower row below the left panel and Viewer; when the right panel is closed, it spans the full workspace width. JPEG adjustments run locally in the browser.

Anshitsu is desktop-first because practical photo development requires adequate space for the Viewer, Scope, Develop controls, and Filmstrip. Narrow layouts should remain usable enough to avoid critical breakage, but a dedicated mobile development workspace, or a Drawer, Tab, or vertically stacked redesign, is outside the current architecture unless explicitly planned separately. Possible future mobile layouts for Anshitsu are separate from the existing desktop-oriented Stack management workspace, which does not support touch Drag & Drop.

The frontend image builds static assets using Vite and TypeScript with Node.js 24, then serves them with nginx. No Node.js or Vite development server runs in the final frontend image. nginx strips the `/api/` prefix before forwarding to `backend:8000`; the browser never connects directly to port 8000. Docker DNS resolution is refreshed so a recreated backend can be found again.

The backend uses Python 3.14, FastAPI, Uvicorn, and HTTPX. `GET /immich/status` calls the stable Immich `GET /api/users/me` endpoint. `GET /immich/about` calls `GET /api/server/about` and returns only `version`, `build`, and `sourceRef` when they are valid strings (each limited to 200 characters), or a safe `error_code`; it never proxies the raw upstream response. Settings treats this optional request independently from photo browsing and the Immich connection status. `GET /assets/recent` calls stable `POST /api/search/metadata`, filters for `IMAGE`, orders by `fileCreatedAt` descending, limits the result to 100, and returns the metadata needed by the grid. `GET /assets/{id}` returns selected non-GPS details and EXIF data. The thumbnail and preview routes proxy Immich-generated images at the corresponding sizes. All Immich calls use the official `x-api-key` header from backend environment variables. The key needs `user.read`, `asset.read`, `asset.view`, `asset.download`, `server.about`, and for STACK management `stack.read`, `stack.create`, `stack.update`, and `stack.delete`. The only Immich writes are explicitly confirmed Stack create/update/delete operations; photo originals and assets are not modified, deleted, or uploaded. The JPEG original route validates asset format and response content type, then streams the official `GET /api/assets/{id}/original` response in 64 KiB chunks. It disables nginx buffering through `X-Accel-Buffering: no`, uses private no-store caching, and closes upstream resources on completion, failure, or client disconnect. The original route retains the existing timeout and redirect policy. A failure after response headers terminates the transfer rather than returning a JSON error inside the JPEG. Redirects are not followed, TLS verification remains enabled, and requests use a three-second connect timeout and five-second HTTPX operation timeout; this is not a total download deadline. There are no retries.

Application code uses only the configured `IMMICH_URL`; it does not know whether Docker DNS, a LAN route, or HTTPS provides the route. Selecting and operating that route is a deployment responsibility.

The status response distinguishes missing URL, missing key, unreachable server, rejected or insufficient credentials, and unexpected API responses using safe error codes and messages. Asset endpoints also return only generic configuration, reachability, authentication, or upstream-response errors. They do not return the upstream response body, URL, API key, or internal exception text. The frontend intentionally reduces these details to concise user-facing states.

For optional local development, Vite provides the same `/api/` prefix mapping to a loopback backend. This is separate from the production nginx configuration.

## Shared Settings and browser preferences

`frontend/src/App.tsx` wraps the routed application in `SettingsProvider` from `SettingsDialog.tsx`. Home and Anshitsu render the same `SettingsButton`; the provider mounts the modal alongside the routes rather than replacing a route. Opening or closing Settings therefore leaves the Anshitsu component tree, active edit session, History and cursor, Filmstrip selection, and autosave timer mounted. Settings preferences use a separate browser `localStorage` layer and the external-store subscription in `appSettings.ts`; storage exceptions fall back to in-memory choices for the current session. These preferences do not enter Recipe, History, SQLite edit snapshots, or image processing versioning.

The `showKeyboardShortcuts` preference uses `genzoroom.showKeyboardShortcuts` and defaults to ON. Its `BinaryRadioChoice` presents ON / OFF as grouped native radios. It controls only explanatory shortcut labels: shortcuts remain active when OFF, ordinary Tooltip descriptions remain, and Menu actions remain available. The preference is separate from Recipe, History, and SQLite edit state.

Display language reuses the legacy `genzoroom.language` key. Stored `en` or `ja` values remain manual choices; absent or `auto` values follow `navigator.languages` in priority order, matching primary subtags against the keys of `LANGUAGE_RESOURCES`. The first supported language wins and English is the fallback. Translation resources are enumerated from that map, so later language resources can be added without changing the preference model. `changeAppLanguage()` stores the selected preference, including `auto`, while changing the active i18next language.

Date and time formatting is independent of display language. `genzoroom.dateLocale` stores an explicit supported locale or defaults to `auto`; `resolveDateLocale()` uses the first browser language accepted by `Intl.DateTimeFormat`, then the runtime's default locale. `formatPhotoDate()` is used by Home photo cards and Anshitsu date and EXIF displays. It uses `Intl.DateTimeFormat` date/time styles and preserves the wall-clock fields of timezone-less EXIF values by parsing and formatting those values in UTC; it does not assign the browser time zone to such capture times. Explicitly zoned values continue through normal browser-local formatting. The browser's time zone is not user-configurable here.

`genzoroom.weekStart` independently stores `auto`, `sunday`, or `monday`. `resolveWeekStart()` returns JavaScript weekday numbering (Sunday `0` through Saturday `6`); Auto uses `Intl.Locale.getWeekInfo()` or `weekInfo` when available, mapping ISO Sunday `7` to `0`. Older environments use a deterministic region fallback (Sunday for US, CA, JP, CN, KR, TW, PH; Monday otherwise). Home Calendar uses this resolved value for both month and year views.

WebGPU retains the existing `genzoroom.webgpu.enabled` key and defaults to enabled unless its value is the literal `false`. The Settings switch reports this saved preference separately from runtime availability and actual GPU drawing. Anshitsu owns `useWorkspaceGpu`; unsupported, failed, or disabled GPU processing uses the existing CPU Worker, then the existing main-thread fallback if the Worker fails. GPU active is reported only after an accepted GPU-rendered Canvas result. Home performs a full pipeline availability probe, then immediately disposes it, and does not retain a processing renderer. Settings changes are subscribed live by the workspace and do not remount it.

`genzoroom.initialImage` stores `auto`, `original`, or `preview`, with `auto` as the default. `prefersOriginal()` resolves Auto to Original only while GPU processing is enabled and available. `useJpegOriginal()` displays the existing preview during its active-photo JPEG request; when an original is ready, Auto or Original preferred selects it. Preview preferred never promotes automatically. A per-photo manual Preview / Original choice is marked manual and takes precedence over later readiness or GPU-state changes. Changing photos resets that photo-specific choice; the existing abort and object-URL release path prevents an old request from replacing or retaining the new photo's source. The preference is not added to recipes or persisted edit state, and Home does not fetch originals.

`SettingsDialog` uses a native modal `<dialog>` with `aria-modal` and a labelled heading, initial focus, Tab / Shift+Tab trapping, Escape and close-button handling, and focus restoration to the opener. Backdrop dismissal requires a primary pointer press and release both outside the dialog bounds, so an inside-originating drag cannot dismiss it. Pointer events are contained, and capture-phase window key handlers suppress background shortcuts while the dialog is open; Anshitsu also blocks its viewer/edit shortcuts for the open interval. Closing the modal does not invoke edit, History, or save operations.

The dialog requests `/api/health`, `/api/immich/status`, and `/api/immich/about` independently, with bounded requests and a manual refresh. The latter is proxied by nginx to backend `GET /immich/about`; `get_immich_about()` reads credentials only from backend environment variables and calls Immich `GET /api/server/about`. The response model `ImmichAbout` exposes only `version`, `build`, `sourceRef`, or a safe error code. The API key is never returned to or stored by the frontend. Immich API keys need the `server.about` permission for the optional server information; permission or network failures do not disable existing photo or edit APIs. Home's compact connection status remains in place.

The Settings implementation and follow-up layout/backdrop changes do not alter Recipe v18, History, the current SQLite schema version 4, or `processingVersion` (`jpeg-preview-srgb8-v1`).

## Docker deployment

`docker-compose.yml` defines two services:

| Service | Container port | Host exposure | Role |
| --- | --- | --- | --- |
| `frontend` | `8080` | `${GENZOROOM_PORT:-3190}` | Static file serving and API proxying. |
| `backend` | `8000` | None | Immich proxying and SQLite edit-state API. |

Only the frontend publishes a host port. Both services join a project-scoped `api` network marked `internal: true`. The frontend also joins a `web` bridge network for its published entry point, while the backend joins a separate `outbound` bridge network for LAN, routed, and HTTPS connections. Joining `outbound` does not publish backend port 8000. The backend bind-mounts one host data directory at `/data`; no host networking, GPU, or privileged mode is used.

The standard `docker-compose.yml` has no dependency on an Immich Docker network. The optional `docker-compose.immich-network.yml` attaches only the backend to an existing external network selected with `IMMICH_DOCKER_NETWORK`. This enables Docker DNS access to an Immich service on the same host without exposing the backend or attaching the frontend to Immich. The external network and Immich service name belong to the deployment environment and are never hardcoded by GenzoRoom. The application still receives only `IMMICH_URL` and `IMMICH_API_KEY`; `IMMICH_DOCKER_NETWORK` is consumed by Compose.

Both containers run as non-root users, drop Linux capabilities, and disable privilege escalation. The backend runs as UID/GID 10001:10001 and requires a writable host data directory. `.env` provides Compose inputs for the host port, Immich connection, and persistence root, but it is not mounted into the application; Portainer can supply the same values through stack environment variables.

Compose starts the backend before the frontend but does not wait for API readiness. Startup failures are visible in container logs and the UI; the user can check again after services become ready. Both services use `restart: unless-stopped`.

The files support builds on a Docker host with Docker Compose. When Portainer is used, a Git Repository stack can use `docker-compose.yml` as its Compose path and, when same-host networking is needed, `docker-compose.immich-network.yml` as an additional path. Portainer must target the Docker endpoint where the external network already exists. The configuration does not provide prebuilt registry images or Swarm deployment support.

See the [deployment guide](deployment.md) for startup, verification, troubleshooting, and removal commands. Removing the Compose deployment removes its containers and networks; copied deployment files and built images remain until explicitly removed.

## JPEG editing foundation

Anshitsu keeps active edit sessions in an in-memory map keyed by Immich asset ID. Each session contains a JSON-serializable flat Recipe v18, committed history entries (`kind`, `before`, `after`), a history cursor, and an optional pending transaction. The recipe has four category flags, three Color Grading range flags (`gradingShadowsEnabled`, `gradingMidtonesEnabled`, `gradingHighlightsEnabled`), sixteen numeric values, and sixteen per-adjustment `adjustmentEnabled` flags. All 23 flags default to true; numeric values default to zero. Category, range, and individual flags are independent, and disabled values remain stored. Recipe v17 is accepted and migrated when reading legacy saved state. Only JPEG assets are editable. Activating a JPEG normally loads its edit state from SQLite before enabling editing. If an Anshitsu session still holds dirty local edits or an unconfirmed save after a failed exit, reactivating that asset keeps the local state and does not replace it with a GET result; explicitly discarding local state removes the record and requires a fresh GET. Dirty edits are autosaved after five seconds of inactivity, and dirty Filmstrip switches save before navigation. The Home control saves all assets edited during the current Anshitsu session, compacting each History before the final save. Browser Back, page reload, and browser or tab close do not trigger a final save; the debounce interval and in-flight edits may therefore remain unsaved.

| Category | Adjustment keys | Enabled flags |
| --- | --- | --- |
| White Balance | `temperature`, `tint` | `whiteBalanceEnabled` |
| Basic | `exposure`, `contrast`, `highlights`, `whites`, `shadows`, `blacks` | `basicEnabled` |
| Color Grading | `shadowsTemperature`, `shadowsTint`, `midtonesTemperature`, `midtonesTint`, `highlightsTemperature`, `highlightsTint` | `colorGradingEnabled`, plus the three range flags above |
| Color | `vibrance`, `saturation` | `colorEnabled` |

Each adjustment also has its own `adjustmentEnabled.<id>` flag. Category, Color Grading range, and adjustment flags are independently editable and independently represented in History; disabling any level bypasses processing while retaining the stored values.

### Edit clipboard and Paste

`frontend/src/editClipboard.ts` owns one module-memory clipboard per browser tab. It stores a detached copy of selected adjustment values plus the source asset ID and filename; it neither references the live recipe nor reads or writes the OS clipboard. Normal Copy stores all sixteen Recipe v18 adjustment values, selected Copy stores the chosen values, and slider Copy stores one value. All three replace the same clipboard. Copy reads the saved recipe values rather than `effectiveAdjustments`, so disabled categories, ranges, and adjustments still copy their retained numbers. None of the 23 enabled flags is copied. The clipboard survives route changes, Home, and reopening Anshitsu within the tab, but not a page reload or tab close.

The Viewer’s `⋯` menu exposes Copy all, Copy selected, Paste copied, and Paste selected. With the Viewer as the keyboard target, Primary+C copies all values unless the existing slider operation target is active; then it copies that adjustment only. `adjustmentFocus.keyboardAdjustment()` is the shared operation-target source for slider keyboard control, including the active hover or focused range input, so Copy does not maintain a second target. Primary+V applies the clipboard values to the active photo without requiring Viewer or slider focus. It is available after the active photo’s edit state loads and is blocked during photo switching, exit saves, a modal selection, or other non-editable states. Primary+Alternate+C and Primary+Alternate+V open the selection dialog while the Viewer is the keyboard target. Anshitsu’s handlers ignore native text-editing targets, composing IME input, AltGraph, repeats, unsupported modifiers, and already handled events. Dialog events are isolated from the workspace; Escape cancels, Space uses native checkbox toggling, Enter confirms from a checkbox unless the selection is empty or the key is repeating, and focused buttons keep their native Enter action. The modal dialog traps Tab navigation and restores the prior connected focus on close. The menu is an alternate entry point when the Viewer is not focused.

Selected Copy starts with all sixteen items checked. The shared dialog groups items under White Balance, Basic, Color, and Color Grading; Color Grading separates Shadows, Midtones, and Highlights. It supports individual and category selection, indeterminate category state, and all-select / clear-all controls. Selected Paste offers only clipboard items and checks every candidate, including values equal to zero; deselected values are omitted from that Paste without changing the clipboard. No empty selection can be confirmed. Items are shared from the recipe’s `ADJUSTMENT_IDS` and category definitions. The Paste reducer applies only the supplied adjustment IDs in one edit action and leaves all 23 destination enabled flags intact. It commits any pending slider edit first and creates one compound History entry only when a value changes. A no-op Paste creates no Paste entry and does not itself discard Redo; a pending slider operation is still committed separately before Paste.

A Paste entry has `kind: 'paste'`, complete Recipe `before` and `after` snapshots, and metadata `{ sourceAssetId, sourceFilename, adjustmentIds }`. The source filename is shown in History. Undo and Redo replay the compound recipes. History compaction processes applied and Redo branches independently and explicitly keeps Paste entries separate from adjacent operations. Clipboard state is transient; Paste itself follows the ordinary edit dispatch, dirty detection, autosave, Filmstrip save, and Home-exit save/compaction paths.

The frontend defines persistence snapshots in `frontend/src/editState.ts` and normally loads them through the edit-state API when a JPEG asset is activated. Snapshot `stateFormatVersion` 2 is independent of Recipe v18 (with v17 read compatibility), SQLite schema version 4, and `jpeg-preview-srgb8-v1` processing version. A snapshot contains the current recipe, full History and cursor, and Immich preview source identity. Creating one commits pending work on a copied session, leaving the live editing gesture unchanged. Frontend and Backend validation reject unsupported versions, malformed recipes or entries, kind/diff mismatches, broken History continuity, and a cursor/current-recipe mismatch without replacing or discarding data. A Paste entry requires exactly typed source asset and filename metadata plus a non-empty, duplicate-free list of known adjustment IDs. Its before / after recipes must be valid, all enabled flags must match, at least one numeric adjustment must change, and every changed adjustment must appear in the metadata list. The validators allow strictly validated v1 snapshots for read compatibility; snapshot v1 uses the legacy History entry form and cannot contain Paste. Reading v1 does not rewrite the database. The next changed save emits a validated v2 snapshot. Paste metadata and semantics are accepted only for v2. A rollback to a release that only understands snapshot v1 may therefore fail to load an asset after a v2 snapshot has been saved. History kinds remain an explicit supported set; unknown future kinds are rejected rather than preserved as opaque entries.

Pure History compaction processes the applied and Redo branches independently, preserves the current recipe, and recalculates the cursor. Consecutive operations on one numeric adjustment or one enabled flag collapse to their first before / last after; a round trip disappears. If a run disappears, newly adjacent matching operations are considered again. Supported Reset kinds and Paste entries stay independent. `COMPACT_HISTORY_ON_EXIT` defaults to true; autosaves and Filmstrip saves use uncompressed History, while the Anshitsu Home exit compacts all session-edited assets.

`useAssetEdits.organizeHistory()` exposes `clearHistory`, `trimHistory`, `resetEdits`, and manual `compactHistory` for the History menus. Clear, trim, and manual compaction retain a deep copy of the previous EditSession only when History actually changes. The next Undo, through either the button or shortcut dispatch, restores that complete session including Recipe, Redo, cursor, and pending work, then consumes the backup. `canUndo` includes this restoration right even at cursor zero; `hasOrganizationUndo` identifies it separately. Reset has no organization Undo.

Any subsequent user edit intent (including a no-op value, Paste, Redo, or History jump), reset, or another organization attempt consumes the previous backup. A successful changed organization replaces it; a no-op or failed attempt creates none. Compaction failure leaves the live session intact. Internal commit callbacks, focus changes, rerenders, autosave, and save responses retain the backup. Photo navigation and Home exit discard it. Backups are transient per-photo records and never appear in snapshots or SQLite. Restoring after a save uses the ordinary dirty detection and save path to write a new revision; unknown PUT results are still resolved with the original request first. Save responses synchronize a compacted live session only if both its session object and fingerprint still match the request's original live state.

History's header menu offers compact, clear, and reset; row context menus additionally offer partial deletion at the invoked row. Both use the same operation definitions and `organizeHistory()` handlers. Right-click or Shift+F10 opens a row menu without jumping. An explicit trim cursor deletes the clicked row and earlier operations atomically: if the live cursor is newer, the live Recipe and pending work remain and the cursor decreases by the removed count; if older, the selected row's after Recipe becomes the starting point at cursor zero and replaces the pending preview. Organization Undo restores the entire original session including that pending work. Initial State's context menu uses the live cursor, with trim disabled at zero. Menus are portaled into a fixed viewport-clamped overlay and close on selection, Escape, Tab, outside pointer action, or photo navigation.

Clear and reset use a native `dialog.showModal()` confirmation with localized Japanese Cancel / Continue (`キャンセル`／`続行`) and English Cancel / Continue buttons. Cancel initially receives focus; its focused state is red and Continue's is gray. Tab/Shift+Tab cycles buttons, Enter activates the focused button, Y continues, and N or Escape cancels. Only reset shows a warning icon and the message “この操作は元に戻せません。” / “This action cannot be undone.”; clear can be recovered by the organization Undo. IME, AltGraph, repeats, handled events, and modified Y/N input are rejected. The modal isolates background keyboard events, prevents other History and clipboard actions, and restores the invoking focus after it is re-enabled. Confirmation is bound to the original asset ID and rechecks edit availability at Continue. Compaction failures show an alert outside History; success adds no explanatory text. Persistence formats and save behavior are unchanged.

Increment `processingVersion` only when the intended output pixels for the same recipe change, such as a gain formula, Color Grading weight, stage order, or color-space meaning. UI, History, storage changes, byte-identical optimizations, and Worker implementation changes do not increment it.

Individual adjustment Reset changes only its value and preserves that adjustment's enabled flag. Color Grading Reset changes its six values in one History operation and preserves the parent, range, and individual flags. All Reset restores all sixteen values and all 23 flags. Individual, category, and range toggles commit pending adjustment edits first, then commit one separate History operation without changing numeric values. Parent categories may be off while child switches change; child settings take effect when their parent is enabled again.

`editing.ts` provides pure begin/update/commit/reset/undo/redo transitions. Preview changes use the current recipe immediately. Pointer release/cancel, control unmount, or 500 ms keyboard/wheel inactivity commits one operation. Keyboard input resets the timer on every accepted keydown; keyup, pointer leave, and focus changes do not commit it early. No-op operations compare the complete recipe, including all 23 enabled flags and sixteen adjustment values, and do not create history or discard redo. A new committed edit after Undo replaces the redo branch. History rows are keyboard-accessible jump buttons; selecting a row restores the recipe after that operation while retaining the Redo branch, and the trailing Initial State row restores the recipe before the first operation. A jump commits pending slider work first and records no new History entry. Each adjustment Reset, individual/category/range toggle, category Reset, and All Reset has a separate operation kind; all are undoable. Category and adjustment resets affect only their own values and preserve enabled flags. All Reset restores all sixteen values and all 23 enabled flags to defaults in one operation. Their History labels stay concise and are localized at display time rather than stored in recipes. The flat in-memory recipe schema is version 18; durable snapshots retain the recipe, full History, and Undo/Redo cursor in SQLite.

`AdjustmentSlider` supplies a compact reusable adjustment row with its label, native range input, synchronized direct numeric input, optional fixed-width unit slot, and inline reset in one responsive grid row. The current rendering path is:

```text
Selected preview or cached JPEG original adapter (editImageSource.ts)
  → browser decode into sRGB RGBA
  → adjustmentWorkerClient.ts (one source copy transferred on initialization; recipes sent per render)
  → adjustmentWorker.ts → adjustmentWorkerRuntime.ts
  → adjustmentPipeline.ts (immutable source → linear-light Temperature → linear-light Tint → linear-light Exposure gain 2^EV → sRGB midpoint Contrast → Highlights → Whites → Shadows → Blacks → masked linear-light Shadows Temperature → masked linear-light Shadows Tint → masked linear-light Midtones Temperature → masked linear-light Midtones Tint → masked linear-light Highlights Temperature → masked linear-light Highlights Tint → Vibrance → Saturation)
  → result buffer transferred to AdjustedImage.tsx → adjusted Canvas → existing Viewer transforms

Decoded source pixels → unadjusted Canvas in the same Viewer position
```

`effectiveAdjustments` substitutes defaults for each disabled category, individual adjustment, and (when Color Grading is enabled) disabled Shadows, Midtones, or Highlights pair. The source recipe retains all numeric values and flags. A disabled individual adjustment becomes its default value; a disabled range bypasses its pair; a disabled category bypasses its full group. These switches do not alter one another. Color Grading Reset clears only its six values; All Reset also turns all 23 flags back on.

The no-op check considers all sixteen effective values and returns exact source bytes when they are zero. Alpha is preserved. Existing White Balance and Basic tone formulas, luminance-region skips, intermediate rounding, and stage order are unchanged. The three Color Grading pairs run after Blacks with the shared weights and gains described below; each active stage clips and rounds before the next.

Vibrance runs after Highlights Tint. It uses `Y = 0.2126R + 0.7152G + 0.0722B`, `chroma = max(|R−Y|, |G−Y|, |B−Y|)`, and `lowSatWeight = 1 − clamp(chroma / 0.5, 0, 1)`. Positive strength is `0.75 × lowSatWeight`; negative strength is `0.6 × (0.25 + 0.75 × lowSatWeight)`. With `factor = 1 + vibrance / 100 × strength`, each channel becomes `clamp(Y + (C−Y) × factor, 0, 1)` and is rounded to 8-bit before Saturation. Zero-valued stages are skipped. Every render starts from the untouched decoded source, so edits do not accumulate clipping from previous renders.

This remains an 8-bit sRGB processing pipeline. Home and Filmstrip use Immich thumbnails. Anshitsu initially displays the Immich preview and acquires only the selected JPEG original in the background, while preview editing continues. JPEG-only captures and Pixel `RAW-01.COVER.jpg` use the same filename-format classification; DNG and other formats have no original acquisition. The compressed original is reused while the asset remains selected and released on navigation or unmount; it is not cached across the Filmstrip. Preview / Original is local display state alongside Before / After and never changes Recipe, History, sourceIdentity, saved-data versions, or SQLite. Both sources receive the same current recipe, including all bypass flags, Undo and Redo. Viewer 1:1 uses the dimensions of the displayed source; switching sources resets zoom/pan to Fit.

JPEG originals decode only when selected for display. An HTML image retains embedded ICC interpretation; drawing into an explicitly verified sRGB Canvas and reading sRGB ImageData performs browser-managed conversion before pixel processing. Display P3 is not relabeled as sRGB. Out-of-sRGB colors are limited by the existing 8-bit working space. No RAW, wide-gamut, HDR, export, or special original-processing interlock is introduced. NAS / Firefox checks confirmed sRGB and Display P3 appearance by visual inspection, not color-difference measurement. Before WebGPU was introduced, repeated adjustment updates on the tested setup using the CPU pipeline took about two to three seconds by user estimate; this was an acceptance observation, not a benchmark, and does not describe current WebGPU performance.

Immich's Asset EXIF response has no ICC profile description field. `jpegProfile.ts` reads bounded JPEG metadata slices from the already-acquired original, assembles ICC APP2 segments, and reads v2 desc or v4 mluc profile descriptions. It does not use EXIF ColorSpace or assume sRGB. Missing ICC and unknown/malformed metadata are displayed separately. The left metadata panel is labelled “Original Info” / “原版情報”; its profile and image dimensions are original-derived and remain visible in either display mode. Profile descriptions do not determine pixel transforms.

### Color Grading weights and shared gains

Let `S(a,b,Y) = x²(3−2x)`, where `x = clamp((Y−a)/(b−a), 0, 1)`. Here Y is calculated from normalized **sRGB bytes**, not linear-light RGB. Each range calculates Y once before its Temperature stage and shares the resulting weight with its Tint stage. The next range uses the rounded output of the preceding range.

| Range | Weight | Full strength | Transition |
| --- | --- | --- | --- |
| Shadows | `1 − S(0.15,0.35,Y)` | Y ≤ 0.15 | Fade out 0.15–0.35; zero from 0.35 |
| Midtones | `S(0.15,0.35,Y) × (1 − S(0.60,0.78,Y))` | 0.35–0.60 | Fade in 0.15–0.35; fade out 0.60–0.78 |
| Highlights | `S(0.55,0.75,Y)` | Y ≥ 0.75 | Zero through 0.55; fade in 0.55–0.75 |

Temperature targets are `(1.5^−t, 1, 1.5^t)` with `t = value/100`; Tint targets are `(1.3^u, 1.3^−u, 1.3^u)` with `u = value/100`. Each range applies `targetGain^weight` in linear RGB. Each active stage clips, encodes, and rounds separately. All ranges use the same channel-gain helper and module-level 256-entry Float64 sRGB decode table. Global Tint shares one LUT for its identical red/blue gains; weighted Tint calculates their identical effective gain once per pixel. These are exact reuse operations, not approximations or stage fusion.

Range thresholds are named constants in three pure weight helpers. Future Point / Width support can parameterize these helpers, but must first define how shoulder-shaped Shadows/Highlights and the Midtones plateau map to those controls, including edge clamping and valid widths. No Point / Width fields or migration system exist in Recipe v18.

### Worker ownership and limits

`AdjustedImage` decodes the source once and retains its buffer for CPU fallback. The CPU Worker client transfers a single copied source buffer to the Worker when that decoded source changes; recipe messages contain no pixel copies. `adjustmentWorkerRuntime` calls the same pure `renderAdjustments()` used by the main-thread fallback, with the complete v18 recipe. It retains its source and transfers the new output buffer back. There is no separate Worker pixel algorithm or per-adjustment protocol mapping. The GPU renderer is available for JPEG preview and selected-original sources only; other assets continue through the existing image display path.

The Viewer keeps Preview / Original and Before / After as display state outside the recipe and History. `AnshitsuPage` owns the persistent Before / After choice across Filmstrip asset switches; `ImageViewer` owns the temporary held-Backslash state, matched by `KeyboardEvent.code`, and the `]` source toggle. `AdjustedImage` draws decoded input pixels into a Before Canvas and Worker/fallback output into an overlaid After Canvas. Comparison changes only the After Canvas visibility, so it issues no render request and leaves the shared Viewer zoom/pan transform intact. A new source clears the previous canvases before its decode/result is displayed. Before bypasses develop adjustments; future geometric transforms should feed both display paths before this split.

The CPU Worker client permits one in-flight render and one pending latest recipe. When a newer recipe is pending, the completed older output is discarded and the latest request is sent. Worker request IDs and asset generations reject mismatched results. RAF coalesces changes before submission. Decode is aborted on source change/unmount; pending RAF is canceled, Worker callbacks are removed, and the old Worker is terminated. Worker startup, initialization, message, and runtime errors use the retained source in the main-thread fallback. GPU scheduling and its separate fallback path are described below.

Each render still needs one output buffer of `4 × width × height` bytes, including an identity result: transferring the retained source would detach it. Main-thread fallback storage, the Worker's retained source, and the additional Before Canvas backing store for immediate comparison are intentional. Small gain/tone LUTs have 256 entries; there are no full-image per-stage buffers. Stage-specific encode/round/decode boundaries preserve current output and cannot be fused without reconsidering that behavior. Full-size CPU pixel work and Canvas upload remain proportional to pixel count. Worker scheduling improves responsiveness but cannot cancel a render already running or reduce its pixel count; sustained latency may require a separately designed reduced-resolution interaction path. No end-to-end Firefox performance claim is made from unit tests.

The Backend stores the current recipe, full Undo/Redo History and cursor, source identity, four separate version domains, revision, timestamp, and last save ID atomically in one SQLite row per Immich asset. `PRAGMA user_version=3` tracks table structure; sequential migrations add the Export Queue at v2 and separate runtime run/item snapshots at v3, preserving all edit-state and Queue columns and data. Connections are opened per operation with WAL, `synchronous=FULL`, and a 3000 ms busy timeout. The GET route returns `{ state: null }` only for an absent row. PUT accepts a validated edit-state snapshot plus `expectedRevision` and UUID `saveId`, returns revision and UTC timestamp, rejects stale revisions, and recognizes an identical retry of the latest save ID. When a network result is unknown, the frontend retains the exact snapshot, expected revision, and save ID and retries that request before sending a newer snapshot. A repeated request that no longer matches the latest DB revision remains a 409 conflict; no automatic merge occurs. Requests are limited to 8 MiB at nginx and Backend. Validation is repeated when reading stored JSON. Invalid payloads return safe 422 codes; unavailable or inconsistent database state returns safe 503 codes without affecting Immich routes. The frontend blocks JPEG edits until GET succeeds, compares snapshots with its last confirmed save, autosaves dirty state after five seconds without an edit, and saves dirty state before Filmstrip navigation. Autosaves and Filmstrip saves preserve full History. The Anshitsu Home control sequentially saves every asset edited in that session, including assets already clean after autosave, and compacts each History before saving. Confirmed compact saves synchronize the live session; partial successes stay committed if a later asset fails. Exit save failures offer stay or exit without saving. Browser Back, reload, and close interception are not implemented. Edited image pixels are not written back to Immich; explicit Stack writes are a separate operation.

### Export Queue persistence and API (Export Phase 1)

The Phase 1–4 sections record each phase's scope at completion. Their later-phase exclusions are historical; current Export management and the JPEG engine foundation are described in Phase 4 and Phase 5A below.

The asset-level Export Queue shares `/data/genzoroom.db` and the per-operation connection helper in `edit_store.py`. Fresh databases migrate sequentially from v0 to v1 to v2. Existing v1 databases gain `export_queue` in one migration transaction; `asset_edit_states` rows, Recipe/History versions, revisions and save IDs are preserved. Reopening v2 does not rerun migrations, future schema versions are refused, and failed migrations roll back their schema changes. For a deployment rollback to a backend that supports only v1, retain a consistent SQLite backup taken before upgrade; restoring that backup also loses later writes. No downgrade or live database replacement is performed by Phase 1.

`export_queue` contains an internal `INTEGER PRIMARY KEY AUTOINCREMENT`, unique `asset_id`, `status`, `queued_at` and `updated_at`. Listing orders by the internal key, never timestamp alone, and does not expose that key. Status permits `queued`, `waiting`, `encoding`, `registering` and `failed`; normal Phase 1 enqueue only inserts `queued`. Both timestamps use canonical UTC millisecond ISO form ending in `Z`; persisted offsets such as `+00:00` and `+09:00` are treated as corrupt storage. No job checkpoint, Recipe snapshot, progress or runtime transition is stored.

| HTTP API (Frontend uses /api prefix) | Contract |
| --- | --- |
| `GET /export/queue` | Returns `{ items: [{ assetId, status, queuedAt, updatedAt }] }` in insertion order; empty is `{ items: [] }`. UUIDs are canonical and timestamps are UTC ISO strings with milliseconds. |
| `POST /export/queue` | Accepts exactly `{ assetIds: UUID[] }`, 1–100 IDs. Canonical duplicate IDs are rejected. All requested persisted snapshots must validate and pass `edit_state.has_non_default_recipe()` on the current Recipe; retained History alone does not make a default Recipe eligible. Missing/no-edit state returns 422 `asset_not_eligible`, corrupt stored state returns 503 `persistence_unavailable`. Eligibility and insertion share `BEGIN IMMEDIATE`. Any failure rolls back the whole batch. Already queued items retain status, order and both timestamps; new items follow request order. Returns the entire queue with the same shape as GET. No Immich request is made. |
| `DELETE /export/queue/{asset_id}` | Removes `queued` or `failed` entries. `waiting`, `encoding` and `registering` return 409 `queue_item_locked`. Absent entries return idempotent 204 success. Delete checks and mutation share one transaction. |

Duplicate IDs return 422 `duplicate_asset_ids`; unavailable storage uses the existing `StoreUnavailable` 503 handling, including `unsupported_db_schema` for future versions. Saved rows alone do not establish eligibility. Queue eligibility, automatic cleanup and Home bulk edit-status use `has_non_default_recipe()`. `has_edits()` retains its existing History-inclusive meaning for other callers. Adjustment values count as non-default even when a category or individual control is disabled.

A newly committed `put_edit_state()` whose current Recipe is default deletes that asset's queue entry within the same save transaction, regardless of retained History; Phase 5C restricts this cleanup to mutable queued/failed intent and preserves active frozen work. A cleanup failure rolls back the edit save as well. Revision conflicts and reused save IDs fail before cleanup; identical latest-save replays return the original acknowledgement without mutating queue state. Edited saves leave queue order, status and timestamps untouched. Logs record enqueue/dequeue outcomes and actual no-edit removals with selected IDs/counts/status codes/timing only; no Recipe or History body is logged, and logger failure cannot fail an operation.

`frontend/src/exportQueueApi.ts` provides `ExportQueueStatus`, `ExportQueueItem`, `listExportQueue()`, `enqueueExportAssets()` and `dequeueExportAsset()`, without React state or UI. Requests propagate `AbortSignal` and use `no-store`. Successful JSON is treated as untrusted: exact top-level/item keys, UUID, status union, real UTC timestamps and case-insensitive duplicate item IDs are checked. DELETE requires 204. Typed errors distinguish duplicate IDs, ineligibility, locked entries, storage unavailability, invalid requests/responses and transport failures. Export encoding, upload, runtime transitions, Queue icons and Export page remain later phases.

### Export Queue frontend and Anshitsu integration (Export Phase 2)

`useExportQueue` owns the Frontend Queue snapshot, indexed asset lookup, unknown/loaded membership, load state and per-asset mutation state. Initial membership remains unknown until a list succeeds; a failed refresh retains the last valid Queue. Same-asset mutations are rejected while different assets may mutate concurrently. Requests use `AbortSignal`; unmount aborts pending work. Enqueue can adopt the Backend's full Queue response when its snapshot is current, while dequeue updates only the target asset.

Queue snapshots use a generation shared across adopted GET results and successful mutations. Refresh records the snapshot generation and mutation start sequence. If a GET races with a mutation and cannot safely replace local membership, it is retained as pending and one refresh runs after the last concurrent mutation settles. An enqueue response replaces the whole Queue only if no newer snapshot or refresh request began since that mutation; otherwise it merges only the requested asset IDs, preventing an older full response from restoring unrelated membership.

The existing `EditedBadge` represents a non-default current Recipe and can represent Queue state in Filmstrip: unknown Queue state retains the legacy edited display, Queue-out uses a dark surface with a light icon, and `queued` reverses those colors. `waiting` is amber, `encoding` / `registering` green, and `failed` red. Busy or locked states disable toggling; `waiting`, `encoding` and `registering` are locked, while `queued` and `failed` can be removed. Queue tooltip and aria labels are localized and include the `Q` hint only when shortcut hints are enabled. A default Recipe with retained History uses a separate, noninteractive Filmstrip-only history icon with localized tooltip and aria label, without Queue colors or status. A default Recipe without History has no badge. Home never displays the History-only icon.

Anshitsu's `Filmstrip` keeps the photo-selection button and interactive EditedBadge as siblings. Photo clicks select the active asset; badge clicks only toggle Queue membership. Active state, `aria-current`, FormatBadge, reveal behavior and Filmstrip keyboard navigation remain on the photo control. The badge is positioned at `bottom: 10px` in Filmstrip; Home positioning is unchanged.

The central `exportQueueToggle` shortcut binds unmodified Q/q and operates on the active Anshitsu asset. Existing guards for native editing, IME composition, repeats, dialogs/menus, settings, transitions and exit/save failures remain in force. A known default current Recipe is excluded from Queue actions, including Q, even while old Queue membership awaits cleanup refresh. For eligible assets, enqueue saves a dirty local edit first, confirms a clean save, checks the current Recipe, then calls Backend enqueue. Retained History alone does not establish eligibility. Unvisited assets do not trigger an edit-state GET solely for Queue eligibility; Backend validation is the final authority. Saving a default Recipe removes its Queue entry transactionally in Phase 1, and Anshitsu refreshes Queue membership after a confirmed default save. A competing mutation cannot permanently discard that refresh. Queue load, enqueue, dequeue and eligibility failures use localized alerts without optimistic membership changes.

### Export Queue Home integration (Export Phase 3)

Home edit status represents only whether the current Recipe is non-default, using the Backend's existing `has_non_default_recipe()` predicate. `has_edits()` keeps its History-inclusive meaning for existing edit-state callers. A default Recipe with retained History is unedited and ineligible for Queue in Home; Anshitsu Filmstrip shows it separately with the existing slider icon as a noninteractive History-only marker, localized label, and reduced opacity. It carries no Queue status or color and does not appear in Home.

Home uses `useExportQueue` for the same unknown/loaded snapshot, stale response protection, mutation guards, and abort behavior as Anshitsu. An interactive PhotoCard badge is a sibling of the photo button: its click changes only Queue membership, while photo clicks and selection/range behavior retain their existing actions. Standalone edited photos enqueue when Queue-out and dequeue when `queued` or `failed`; `waiting`, `encoding`, and `registering` are locked. Queue errors retain the known snapshot and are localized.

A Stack representative is ON when any member is in Queue, including partial Stacks; Home does not display a separate partial state. Turning it ON enqueues only members whose current Recipe is non-default. Turning it OFF removes all currently queued members. Member IDs are deduplicated, then enqueued sequentially in chunks of at most 100, matching the API limit. A chunk failure stops later chunks, keeps successful work, refreshes Queue state, and shows an error without rollback. Dequeue remains asset-by-asset with the same partial-success and refresh behavior. Locked Stack members prevent the operation.

In Recent, Favorites, Album detail, and Calendar date detail, Q applies one direction to selected eligible cards. Unedited, History-only, and unknown edit-status cards do not affect direction. If any eligible representative is Queue-out, Q enqueues only Queue-out representatives and leaves ON representatives, including partial Stacks, untouched. If all are ON, Q removes every queued member of those selected representatives. Enqueue IDs are deduplicated and sent in ordered chunks of at most 100; a failure stops the remainder, retains successful chunks, refreshes Queue state, and does not roll back. Multi-dequeue retains successful removals and refreshes after failure. The selection is preserved. Unknown Queue membership, a locked selected member, busy mutations, and repeat invocation do not start a conflicting batch. The Home Q handler also rejects events originating in any `input`, while other Home shortcuts and Anshitsu retain their existing guards and behavior.

Home Queue badges use the shared Queue-state colors: dark/light for Queue-out, inverted light/dark for `queued`, amber for `waiting`, green for processing, and red for failure. History-only opacity and Filmstrip positioning are scoped to Filmstrip; they do not affect Home Queue badges. The Export page, actual export execution, encoder, and Immich upload are not implemented.

### Current Gallery Queue safeguards

Gallery representative badges, multi-selection Q, STACK context-menu rows, Anshitsu Filmstrip controls, and Export management all use `useExportQueue` as the Queue operation gate. Adding requires a confirmed edit-state `true` and a confirmed Queue-out state; removing requires confirmed `queued` or `failed` membership and does not depend on Recipe edit state. The existing multi-selection direction rule remains: eligible Queue-out cards are added when any eligible selected card is Queue-out; otherwise registered selected cards are removed. `waiting`, `encoding`, and `registering` remain locked. Queue status and edit status are independent: context-menu rows retain known edited candidates and registered members, while partial/error edit-state results remain visible as warnings; unavailable Stack members are not presented as an empty candidate set.

`useExportQueue.loaded` describes whether a display snapshot has ever been loaded; its separate `canonical` state determines whether that snapshot can authorize a mutation. Cached rows may remain visible after an uncertain operation, but the hook-level mutation guard blocks enqueue, dequeue, and retry until a current Queue GET is accepted. Network failures, invalid success responses, 408/5xx, and unclassified unavailable responses are outcome-unknown. The Backend's `persistence_unavailable` and `unsupported_db_schema` errors are confirmed refusals: Queue mutations roll back their SQLite transaction before returning these codes. A successful, unsuperseded GET restores operation availability; a failed GET leaves it blocked. Gallery view changes retry the existing refresh path after a failed recovery. Mutation and GET generations continue to prevent older responses from replacing newer accepted Queue state.

`useEditStatusesSnapshot` retains successful batches and reports `partial` when other batches fail or time out, `error` when none succeed, and `ready` on complete success. Its existing eight-second timeout aborts outstanding requests and settles visible state; dependency replacement and unmount also abort, but stale cleanup results are ignored. Queue membership never converts an edit-state `partial` or `error` into success. An unavailable member snapshot is reported separately from a normal zero-candidate result.

### Backend JPEG engine foundation (Export Phase 5A complete)

The engine boundary is future Export Orchestrator → Renderer → `RenderedImage` → Encoder. The current diagnostic orchestrator in `export_engine_diagnostics.py` acquires a saved Recipe revision and JPEG original, then calls the reusable codec and renderer. It does not execute the Export Queue or register output in Immich. `RenderedImage` is an immutable, dimension-validated boundary containing packed row-major, full-resolution sRGB RGB8 bytes (three bytes per pixel), without source metadata or Recipe state. The `Renderer` protocol allows a future renderer replacement without coupling Recipe math to acquisition or JPEG compression.

`jpeg_codec.py` uses Pillow/ImageCms (LittleCMS) to decode JPEG originals, normalize EXIF Orientation 1–8, and convert embedded ICC profiles to sRGB before exposing RGB8. Untagged RGB and grayscale are supported; malformed/unusable ICC and untagged CMYK fail safely rather than guessing colors. Pillow decompression-bomb limits remain enabled, with warnings also treated as failures. Decoder images/transforms are request-local and closed, and compressed source buffers are released after decoding.

`JpegRenderer` uses NumPy Float64 arithmetic with the same Recipe v18 meaning, category/individual enable flags, stage order, clamping, and byte-rounding boundaries as `adjustmentPipeline.ts`: Temperature → Tint → combined Exposure/Contrast → Highlights → Whites → Shadows → Blacks → shadow/midtone/highlight grading pairs → Vibrance → Saturation. Each 3WAY pair shares its pre-Temperature weight. Temperature/Tint (including grading), Vibrance and Saturation normalize accepted fractional settings to integers before gain math, matching Frontend. Half ties follow JS `Math.round`, not NumPy ties-to-even. Input pixels and Recipe are not mutated; an effectively neutral Recipe reuses immutable source bytes. Pixel chunks of 16,384 cap additional float temporaries, while input/output byte buffers retain full resolution. Independently frozen SHA-256 compatibility fixtures in Frontend and Backend detect pixel drift, alongside fractional-setting, enable-flag and chunk-boundary tests; expected hashes must not be regenerated from the implementation under test.

The Encoder uses Pillow to produce a full-resolution JPEG at quality 95, subsampling 0 (4:4:4), with embedded sRGB ICC. Its default diagnostic call remains metadata-free; Phase 5B supplies separately reconstructed EXIF/XMP through optional keyword arguments. The Docker backend is Python 3.14 with pinned Pillow 12.3.0 and NumPy 2.5.3; Pillow is not the pixel-adjustment renderer.

Decode/render/encode run together through `run_in_threadpool`, outside the async ASGI event loop. There is no persistent image cache or temporary-file artifact. Request-local buffers and immutable inputs avoid shared render state. Frontend Abort cancels the client request and suppresses stale results; it does not guarantee interruption of an already-running synchronous Backend worker. Heavy 12MP Recipes have user-reported render times around 12–13 seconds and total processing around 14 seconds; this is the current CPU baseline, not a performance guarantee. Renderer optimization, GPU/process-pool execution, RAW development, and NAS iGPU support are not implemented. A replaceable renderer and eventual shared RAW preview/full-resolution pipeline remain future directions; LightCraft is an unselected candidate.

### JPEG artifact preparation (Export Phase 5B complete)

`export_artifact.py` exposes immutable `ExportArtifact(filename, jpeg)` and `create_export_artifact(source, source_filename, family_filenames, rendered, timestamp=...)`. It determines the filename, validates the source through the unchanged `decode_jpeg()` (including critical ICC), discards that validation RGB buffer, prepares metadata through `jpeg_metadata.py`, and calls the shared Encoder. Standalone preparation consequently performs an additional source decode; it retains no source image/cache after the call. Recipe/Renderer pixel math and `RenderedImage` remain metadata-free. The Phase 5C internal runtime below consumes this artifact boundary; production upload/registration, tag and Stack/COVER writes remain unconnected. The Immich `GenzoRoom` tag belongs to Phase 5E registration.

`filename_family()` mirrors Frontend Phase 0 `stackCandidateDetection.filenameFamily`: an extension is required, a terminal dot is invalid, the first-dot root loses only one terminal case-sensitive `-Genzo[0-9]+`, and an empty/ECMAScript-whitespace-only base is invalid. `next_export_filename()` accepts caller-supplied family filenames, ignores unrelated families, includes the source itself, and chooses maximum terminal suffix + 1 without reusing gaps. Output is `<base>-GenzoNN.jpg`, minimum two digits, without truncating larger values. Decimal-string comparison/increment supports arbitrarily long numbering without Python's decimal conversion limit. Output roots reject path separators, control characters and Windows reserved filename punctuation. There is no existing filename-length cap to inherit; this logical filename layer adds none. Filesystem/upload-specific length constraints and complete family lookup/collision reservation belong to future orchestration. These pure functions do not mutate inputs or search Immich.

EXIF is reconstructed with Pillow's standard `ExifTags.Base` / `GPS` IDs ([Pillow definitions](https://pillow.readthedocs.io/en/stable/_modules/PIL/ExifTags.html)). Preserved IFD0 fields are Make, Model, Artist, Copyright and ImageDescription. Capture fields are DateTimeOriginal, OffsetTimeOriginal, SubsecTimeOriginal, LensMake, LensModel, LensSpecification, ExposureTime, FNumber, ISOSpeedRatings (standard PhotographicSensitivity tag 0x8827), ExposureBiasValue, ExposureProgram, MeteringMode, Flash, FocalLength, FocalLengthIn35mmFilm, WhiteBalance, LightSource, SceneCaptureType, ExposureMode and DigitalZoomRatio. GPS is rebuilt field by field for LatitudeRef/Latitude, LongitudeRef/Longitude, AltitudeRef/Altitude, TimeStamp, DateStamp and ImgDirectionRef/ImgDirection. Dates, offsets, text, integer/rational representations and GPS coordinate/time ranges are checked. Malformed optional fields are dropped individually; an unreadable optional EXIF/XMP container falls back to regenerated metadata after successful source validation. Source JPEG and critical ICC failures remain fatal. EXIF ASCII fields containing non-ASCII text are unsupported and dropped; Unicode user text is supported through XMP.

XMP preservation supports standard Dublin Core title, description (including caption), rights as language alternatives, creator as an ordered sequence and subject/keywords as a bag, plus XMP Rating (-1 through 5) and Label. Simple element/attribute properties and their standard RDF arrays are accepted; language alternatives retain validated language labels. A fresh UTF-8 XML tree escapes user text and has deterministic field ordering. The supported schemas follow [Adobe Dublin Core](https://developer.adobe.com/xmp/docs/xmp-namespaces/dc/) and [XMP Basic](https://developer.adobe.com/xmp/docs/xmp-namespaces/xmp/). IPTC values already represented by these standard XMP properties are supported. Legacy Photoshop APP13/IPTC IIM, extended XMP packets, private namespace aliases, arbitrary structured properties and other IPTC Core/Extension fields are recognized as outside this preservation boundary and omitted; there is no proprietary parser, raw packet copying or string replacement.

Each artifact captures one timezone-aware instant, normalizes it to UTC and uses whole seconds for EXIF DateTime and XMP ModifyDate/MetadataDate; EXIF OffsetTime is regenerated as `+00:00`. DateTimeOriginal retains source capture time. Software and XMP CreatorTool are `GenzoRoom`; Orientation is 1, PixelXDimension/PixelYDimension are the supplied normalized rendered dimensions and ColorSpace is sRGB (1). A fresh sRGB ICC is always embedded. Body/camera/lens serials, MakerNote, private/vendor/RAW tags, source Software/Orientation/dimensions/ColorSpace/ICC, thumbnails/previews, Motion Photo, MPF, appended MP4, Ultra HDR/gain maps, Google Container and source JPEG structure never enter the allowlist. No embedded thumbnail is generated.

Safety constants are 16,384 UTF-8 bytes per XMP text (ASCII bytes for EXIF), 128 RDF array items, XML depth 12 and 1,024 XML elements. Source standard XMP is limited to 65,504 bytes; DTD/entity declarations are rejected by the parser before expansion, including UTF-16 declarations. Generated EXIF is limited to the APP1 payload maximum 65,533 bytes and XMP to 65,504 bytes (65,533 minus its 29-byte header). Aggregate overflow fails with `metadata_too_large`, never truncating an APP1 segment; serialization failures use `metadata_encode_failed`. The codec independently enforces those output limits. Safe artifact errors include `invalid_export_filename`, `invalid_export_timestamp` and existing codec errors. Structured warnings identify optional preservation drop/counts and aggregate rejection; an artifact-level terminal error records only its safe error code. Logging failure does not affect generation, and no metadata values, filenames, XML, paths or pixel buffers are logged.

### Persistent Export Runtime foundation (Export Phase 5C complete)

Schema v3 adds `export_runs` and `export_run_items` beside the unchanged edit-state and Queue columns. Migration v2 → v3 is part of the existing `BEGIN IMMEDIATE` migration transaction, preserves all rows/order/save IDs, rolls back on any DDL error, and refuses future versions. Run rows hold ID, lifecycle (`active`, `completed`, `failed`), optional worker UUID and UTC timestamps. Item rows hold explicit target position, asset ID, original Queue row ID, frozen Recipe revision/version/processing version and Recipe JSON, lifecycle, fixed failure code, confirmed registered asset ID and timestamp. Neither History nor source/JPEG bytes enter these tables. A rollback to a schema-v2-only backend requires restoring a consistent pre-migration SQLite backup; no downgrade is implemented, and restoring a backup loses subsequent writes.

`export_runtime_store.create_export_run()` accepts 1–100 ordered UUIDs, only from `queued`. One writer transaction rejects duplicates, missing Queue/edit state, locked/failed status, malformed saved snapshots and default Recipes before creating any run. It captures the validated current Recipe (v18, matching the current Renderer), revision and processing version, persists target order, and moves every selected Queue item to `waiting` at one commit. Later Queue additions or frontend armed changes do not join that run. Later edit saves or deletion of an edit-state row cannot replace the frozen Recipe. Existing v17 edit-state read compatibility remains intact, but v17 is not an eligible Runtime rendering version. Non-target Queue entries and all `queued_at`/insertion IDs retain their meaning.

`ExportRuntime.start()` is an internal async contract, with no production Start endpoint or frontend connection. Production lifespan creates an unconfigured coordinator and only inspects persisted active work. Start rejects before DB writes unless source, complete family-filename provider and registrar are explicitly supplied. Existing Immich helpers can acquire one asset detail and original JPEG; no existing limited helper proves complete first-dot family membership, so the `FamilyFilenameProvider` boundary awaits Phase 5E. There is no new library scan, incomplete family fallback, production no-op registrar or deliberate unimplemented-registration failure. The Export button stays disabled.

The coordinator holds a strong reference to one detached worker task; an in-process async lock rejects duplicate starts. The worker creates the run with a worker UUID under the DB writer lock. A unique active-run index protects separate coordinator instances, an active-asset index prevents concurrent membership, and each transition checks run/worker ownership, exact Queue row identity, expected status and serial target order. Run/item lifecycle and Queue status/timestamps change atomically. Replacing a Queue row cannot authorize a stale worker. Consistent read transactions validate frozen snapshots, lifecycle, active Queue identity/status/timestamp and serial state shape before accepting recovery work.

One asset passes through frozen item → source detail/original acquisition → complete family context → `encoding` → Decoder → `JpegRenderer` → Phase 5B `ExportArtifact` → `registering` → `ExportRegistrar.register(source, artifact, context)`. Context contains run ID, target position, asset ID and frozen versions/revision. Decode/render/artifact generation and SQLite operations use the threadpool; CPU work never runs on the ASGI event loop. Source streams close on success/failure. The source bytearray is cleared before registration, pixel temporaries stay inside the threadpool call, and artifacts are released when the item completes. The worker retains frozen Recipe metadata across the run, never all targets' images/artifacts. Request completion, navigation and caller cancellation (including while run creation commits) do not cancel its task.

Normal transitions are `queued → waiting → encoding → registering → succeeded/remove`. Only a registrar's explicit `RegistrationResult` with a confirmed asset UUID permits atomic owned-registering completion and Queue removal. Tests inject a fake registrar; production has none. A source/family/encoding/registration failure becomes a fixed allowlisted code and `failed`, leaves that Queue item, and continues the remaining frozen targets without retry. A run finishes `completed` only if every item succeeded; otherwise its terminal lifecycle is `failed`. DB/ownership faults and unexpected coordinator interruption stop the worker and preserve recoverable active state rather than guessing a reset. Provider/registrar exceptions are isolated from internal persistence errors even when their exception types overlap. Logs contain safe IDs, revisions, counts, byte counts, lifecycle and fixed codes, without filenames, Recipes, binaries, URLs, credentials or raw exception text; logging failure does not affect work.

Default Recipe saves remove only mutable `queued`/`failed` intent; `waiting`/`encoding`/`registering` rows remain locked and use their frozen Recipes. Ordinary DELETE still rejects those active statuses. Phase 5D extends this foundation with the lifecycle and recovery policy below. Actual Immich family lookup/upload/tag/Stack/COVER integration and production Start remain Phase 5E; real NAS/Immich integration testing remains Phase 5F.

### Stop, Retry and restart recovery (Export Phase 5D complete)

Schema v4 transactionally rebuilds the v3 run/item CHECK constraints while preserving existing columns, Queue order and frozen snapshots. Runs gain `stop_requested` (default false), nullable `current_position`, and terminal `stopped`; items gain terminal `released`. Existing encoding/registering items become the current item during migration; waiting remains unstarted. Recipe/History/edit-state formats are unchanged. Reverting to a v3-only backend requires a consistent pre-migration SQLite backup; no downgrade is provided and restoration loses later writes.

The worker claims the first active item as current in `BEGIN IMMEDIATE` before source acquisition. Stop and claiming the next item use that same DB write boundary. Stop persists its request and lets the current waiting/encoding/registering item finish. Its success/failure transaction clears current and releases only remaining waiting items: Queue becomes queued, historical run items become released. If no current exists, Stop releases immediately. Duplicate Stop is idempotent, including after completion. A released suffix yields stopped; without released items, all succeeded yields completed and any failure yields failed. Stop is logged at info, not error. `_read_run()` validates serial order, current position, lifecycle, released suffix and exact active Queue row identity/status/timestamp; released and failed historical rows may coexist with later Queue intents/runs.

`POST /export/queue/retry` accepts 1–100 unique asset IDs. It validates every target as failed and currently eligible with a valid supported saved Recipe before updating any Queue row. Queued, active and missing items are rejected (409); duplicates/invalid inputs/default Recipe eligibility use 422, storage/corruption uses 503. Retry retains Queue order and changes only failed intent to queued; historical failed run items, errors and frozen Recipes are unchanged. A later run freezes the then-current saved revision/Recipe. Retry does not launch a worker.

`GET /export/runtime` projects the single active run as `{runId,status,stopRequested,stopAllowed,currentAssetId}`, or explicit null/false idle fields. `POST /export/runs/{runId}/stop` returns the same shape for that run. Responses expose no Recipe, worker token, upstream text or binaries; malformed export requests return a fixed code. There is no Start endpoint, hidden diagnostic Start, WebSocket or SSE.

`ExportRuntime.recover()` dispatches a detached worker using the same instance start lock and process-wide worker lock as normal Start. Transactional reclaim compares the observed old worker UUID, assigns a new one and resets current encoding/registering plus its Queue row to waiting while retaining current position and stop intent. Source/decode/render/encode are regenerated from the frozen Recipe, then registrar is invoked from the beginning. No partial artifact/checkpoint is reused. Unstarted waiting items resume in order; a persisted Stop completes only the recovered current item and releases the rest. Old ownership cannot transition anything. This is a single Backend process/restart design, not a distributed worker lease. Shutdown cancellation preserves checkpoints; HTTP/browser disconnection does not cancel the worker. Storage/ownership failures halt with active state intact; ordinary item failures continue unless Stop is pending.

FastAPI lifespan calls recovery, but current production source/family/registrar dependencies remain unconfigured. Recovery is explicitly deferred without claiming/mutating work or supplying a fake success. Automated tests inject a real JPEG pipeline and fake registrar to verify replay. Actual Immich registration idempotency/duplicate tolerance belongs to Phase 5E.

Frontend polls the small runtime projection every two seconds and refreshes canonical Queue while active and when it finishes. Waiting is light amber, encoding/registering green with indeterminate activity, Stop requested yellow, and failed red (`出力失敗` / `Export failed`). Queued/failed remain mutable and active states remain locked. Selecting only failed cards enables single/bulk Retry; mixed selection is disabled. Retry refreshes canonical Queue even after atomic rejection. Only recognized active runtime replaces the disabled production Start button with Cancel; requested Stop disables it. The exact explanation is `現在の出力処理を終了後、以降の出力をキャンセルします。` / `Cancel remaining exports after the current export finishes.` Retry/Cancel create no W/Q Undo record; existing records still respect current locks. Stale polls cannot overwrite Stop acknowledgement and unmount clears timers/requests.

Family discovery may see that uploaded filename and choose a later candidate, but the filename is not embedded in JPEG metadata, so it does not defeat checksum recovery. The existing remote asset retains its original uploaded filename. No JPEG cache, binary DB storage, fine-grained remote checkpoints or distributed transaction is added. Queue removal still occurs only after complete registrar success and the owned registering commit.

Frontend Start eligibility lives in `useExportManagement`: confirmed idle runtime, loaded canonical Queue, 1–100 armed `queued` targets in Queue order and no conflicting mutation. Selection is independent. Start and Stop reuse the existing confirmation dialog with Cancel initially focused. A synchronous intent guard consumes each confirmation once; IDs and runtime are checked again before submission. Accepted Start clears those armed IDs even if the run terminates before polling observes active status. Existing two-second polling reconciles canonical Queue, selection and status bars. Stop retains Phase 5D's current-item completion semantics and exact Japanese/English wording. Start/Stop/Retry/success add no W/Q Undo record. Leaving Export dismisses a pending confirmation; request/route lifetime never controls the Backend worker.

Required API key scopes are `asset.read`, `asset.view`, `asset.download`, `asset.upload`, `tag.create`, `tag.asset`, `stack.read`, `stack.create` and `stack.update`; the user also permits asset/tag updates and Stack deletion for existing management features. Immich's internal AssetUpdate access check is distinct from API key `asset.update`. Registration exposes only fixed `registration_failed`; structured logs distinguish upload/tag/Stack-context/Stack phases with safe IDs/counts. Raw response bodies, exceptions, credentials, URLs, filenames, Recipes and JPEG bytes remain excluded, and diagnostic failures cannot fail HTTP operations.

Partial remote success is retained, without rollback Asset/Tag deletion. Active-run restart replay differs from terminal failed-item Retry: Retry creates new Queue intent, and a later Start freezes the latest Recipe with a new timestamp, potentially leaving a prior partial output. Concurrent remote changes between Stack read and write cannot be atomically guarded across services; response mismatch is detected but has no automatic rollback. Filename allocation has no distributed reservation and rare duplicate output remains possible. Recovery supports one Backend process, and byte stability assumes unchanged source and rendering/codec versions. Phase 5F must verify actual permissions, upload/duplicate behavior, archive/stacked family discovery, Tag reapplication, child-source Stack merging/member preservation/COVER, source Timeline/capture metadata, Stop and registration restart on the real deployment.

#### Structured Logs

Frontend and Backend have independent opt-in structured loggers with levels `off`, `error`, `warn`, `info`, and `debug`. Levels are cumulative: `error` retains errors; `warn` adds warnings; `info` adds informational events; `debug` includes all events. Both default to `off`. Severity describes the effect on GenzoRoom work: required-operation failures are errors, recoverable abnormal states are warnings, significant lifecycle outcomes are info, and detailed request/state evidence is debug. The Logs tab reads and sets each source's level independently, clears either or both buffers, refreshes Backend snapshots, exports Frontend / Backend / combined JSON, and filters the console to ALL, Frontend, or Backend.

The Frontend ring buffer retains up to 1,000 entries; Backend retains up to 5,000. Both drop the oldest entry when full and report `droppedEntryCount`; clear resets entries and that counter. Context is projected to safe technical fields and limited to 4,096 bytes. Backend additionally limits context structure size; the loggers do not capture stdlib, Uvicorn, HTTP client, browser-console, or raw request/response output. Export uses `schemaVersion: 1` structured JSON reports with UTC timestamps; the viewer formats timestamps in the local browser timezone. Diagnostic fields remain subject to the privacy boundaries in `AGENTS.md`.

Backend Immich instrumentation records logical request start, response, and failure events with safe method, endpoint, status, duration, request/correlation IDs and outcomes. Stack apply adds operation-level and batch-level diagnostics, including operation correlation, phase/result, counts and timing. Diagnostic-only verification or extra network work is restricted to DEBUG. Logging failure does not fail the underlying operation.

### Histogram collection and Scope display

collectHistogram() in histogram.ts is a DOM-independent pure function over the decoded RGBA Uint8ClampedArray. It counts the 8-bit sRGB R, G, and B code values directly into 256-bin Uint32Arrays and ignores alpha. Y′ uses the nonlinear code values with 0.2126R′ + 0.7152G′ + 0.0722B′, rounded with Math.round and clamped to bins 0–255. The function does not alter its input, and each channel's bin total equals the number of pixels.

After a source decodes successfully, AdjustedImage computes its Before histogram once and retains it with that decoded source. After the existing renderAdjustments() produces an adjusted buffer, the Worker computes the After histogram from that buffer and returns it alongside the transferable pixel buffer. The main-thread fallback renders once and calls the same collector on its output. No histogram path reads pixels back from Canvas or reruns the image pipeline.

AdjustmentWorkerClient accepts results only when requestId and assetGeneration match the in-flight request. If a newer recipe is pending, it discards the completed result and sends the latest recipe. AdjustedImage reports an adjusted histogram only after the matching pixel result is accepted by the After Canvas. It carries a sourceKey; AnshitsuPage stores the pair with its assetId, rejects callbacks that do not match the current asset and source, and exposes data only when both identities match. The before and after values are independently nullable. null means that result has not been collected; it is not a zero-filled distribution.

The Viewer reports its effective display state (persistent Before OR held Backslash) to AnshitsuPage, which selects the matching histogram without substituting the other one when it is unavailable. Comparison changes only the displayed data and does not cause another render or collection. ScopePanel owns the non-persistent RGB selection, Y Only state, and Normal / Expanded scale state; these remain in place when the active photo changes. At least one RGB channel remains selected. Normal mode uses the maximum bin across all three RGB channels as a shared scale, regardless of individual visibility. Expanded mode computes nearest-rank P99 over all 768 RGB bins, or the 256 Y′ bins in Y Only. Zero bins participate; the ceiling is at least one. Values above it are clipped to the SVG plot edge without changing histogram data. The responsive graph uses the available Scope region, with the existing compact-layout size override.

Scope shortcuts use KeyboardEvent.code: Numpad 0 toggles Y Only, Numpad 1–3 toggle R/G/B, and Numpad Decimal toggles the scale. While Y Only is active, Numpad 1–3 first restore the previous RGB view without toggling its channel. Scope ignores processed or composing events, modifier combinations, native editing targets, blocked workspace actions, and open menus or dialogs. AdjustmentSlider also excludes these five physical keypad codes from its global arrow-key handler because NumLock-off Numpad keys can report arrow names; native text and number inputs are checked first and retain their browser input behavior.

### Save outcomes and edit indicators

When PUT may have committed but its result is unknown (including HTTP 408 or 5xx and an unreadable or invalid success response), the frontend retains and retries the identical snapshot, expected revision, and save ID before attempting later edits. A confirmed retry advances the revision and allows newer edits to save. A genuine 409 remains a conflict and is not automatically merged. After a failed-save discard, the UI keeps confirmed persisted edit status when known; if persistence cannot be determined, it invalidates the earlier batch result and treats the marker as unknown until refreshed. Browser Back, reload, and tab close still have no forced-save interception.

## Portability and validation

The Windows workspace is only a development directory. Application code and deployment files must not depend on its absolute path or Windows-specific runtime behavior. Deployment must not modify Docker host OS settings or install application files into host system directories. Persistent data uses the explicitly declared `/data` bind mount.

The validation workflow is to develop locally, copy or deploy the required files to the target Docker host, start them with Docker Compose (or Portainer when used), and verify actual behavior there. Successful Windows checks alone do not constitute completed runtime validation.

The deployment runtime check is to open the Web UI, confirm `Backend: Connected`, `Immich: Connected`, and up to 100 recent thumbnails, obtain `{"status":"ok"}` from `/api/health`, and obtain a connected result from `/api/immich/status`. Also verify the empty and failed photo-list states, missing Immich settings, rejected credentials, and the backend stopped.
