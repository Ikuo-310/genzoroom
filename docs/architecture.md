# Provisional Architecture

**Current implementation — authenticated photo browsing, Anshitsu, Recipe v18 JPEG adjustments, History, and persistent edit state are implemented. RAW development is not implemented.**

This document describes the current implementation and possible future extensions. The architecture remains provisional: components, interfaces, and deployment choices may change during development.

React Home has four tabs: Recent, Albums, Calendar, and Favorites. Recent requests 50–500 Timeline images in steps of 50 (100 by default); Favorites requests favorited Timeline images; Albums lists collections and loads assets when a collection is opened. Calendar has year, month, and date-detail views. Its availability and minimum year use Timeline IMAGE assets so Archive-only or video-only dates are not marked as photo days; month thumbnails use the first eligible non-RAW IMAGE in Timeline order. The calendar controls stay sticky inside their scroll region.

Recent, Favorites, Album details, and Calendar date details use one shared photo-card grid with independent per-tab RAW / Non-RAW and edited / unedited filters, adjustable thumbnail size, edited and format badges, and ordered multi-selection with Shift+click ranges. Each photo view has its own selection state. `photoView` in `GalleryPage.tsx` resolves the active photo grid's assets, load state, selection, and edit-status inputs; Album lists and Calendar year/month views have no active photo view. `usePhotoSelection()` owns one view's selected IDs and range anchor while GalleryPage keeps one instance per photo view. Tab-specific filters use session storage; thumbnail size uses browser-saved Settings.

Home keeps in-memory scroll offsets by view: Recent, Favorites, Album list and each Album ID, and Calendar year, month, and date. On Anshitsu navigation, Home passes its tab, detail context, calendar mode, and scroll coordinates in route state; the route validates that context and restores after the required view data is ready. Ordinary tab navigation uses the same view keys and pending restoration mechanism. Album-detail and Calendar-date selections remain available when switching tabs; reactivating their already-active tab returns to the parent view. These rules remain coordinated in GalleryPage rather than being spread across data hooks.

### Stack management drafts

Home passes its ordered selection of concrete assets, including RAW and Favorites assets, and its return context to `/stack`. This route passes those assets directly and bypasses the Anshitsu workspace asset resolver. Automatic detection creates local draft Stack groups and does not modify Immich. An asset with `stackId != null` is excluded from candidate detection. NAME candidates require at least two assets in the same filename family, with at least one RAW and one Non-RAW asset. Families use an exact basename match (removing only the final extension) or normalization of the known Pixel RAW filename pattern. NAME candidates take priority and do not require EXIF evidence. When filename families do not match, a fallback candidate may be created only for a unique RAW / Non-RAW pair whose TIME, CAM, and GPS evidence all match; ambiguous relations and groups larger than two remain unmatched. A fallback group reports NAME as mismatch and the three EXIF signals as matched.

Asset details are requested for NAME candidate members and, when the remaining non-Stack selection contains both RAW and Non-RAW assets, those remaining assets that could participate in fallback matching. Existing Immich Stack assets are never requested. The hook uses at most four concurrent requests per generation. Re-detection aborts the previous generation; cleanup aborts on unmount, and generation checks prevent stale responses from replacing current evidence. Partial detail failures retain NAME candidates and prevent failed members from entering fallback groups.

NAME, TIME, CAM, and GPS evidence each use four states: `matched` (green), `mismatch` (yellow), `unavailable` (dark and inactive), and `error` (red). A mismatch means values were evaluated and differed; it is not an operational failure. Fallback NAME mismatch is explained as a filename-family mismatch. Missing information such as absent GPS is unavailable, while failed detail retrieval or unusable present values are errors. TIME compares EXIF `date_time_original`: when every member has a valid value, a maximum spread of two seconds is matched and a larger spread is mismatch; missing data is unavailable. CAM requires both make and model for every member and compares the pair case-insensitively; missing fields are unavailable. GPS requires valid latitude and longitude for every member and compares coordinate spread within the existing tolerance; missing GPS is unavailable. Backend Asset detail exposes latitude and longitude as optional EXIF fields, preserving compatibility when they are absent.

The automatic COVER is selected from `RecentAsset.date`, preferring the latest JPEG, then the latest Non-RAW asset if no JPEG exists, then the latest member if there is no Non-RAW asset. Valid dates take precedence over unavailable dates; ties preserve Home selection order.

Selected existing Immich Stacks are resolved in one read-only `POST /stacks/resolve` batch (at most 100 requested IDs), using one upstream `GET /stacks`. The shared membership validation rejects duplicated Stacks or members and missing primaries; requested Stacks additionally require at least two complete IMAGE assets. Unknown requested IDs, malformed members, and upstream errors fail the whole batch. Full members carry identical Stack ID, primary ID, and member count metadata. `useSelectedImmichStacks` owns abort, generation checks, failure status and retry. Full membership is resolved before auto-detection inputs are formed, so even a selected asset with stale non-Stack metadata cannot appear both in an Immich group and an auto group.

An imported draft has `origin: immich`, a distinct `draft:immich:` UI ID, `immichStackId`, `originalPrimaryAssetId`, and immutable `originalMemberIds`. Its initial COVER is the upstream primary, and upstream member order is preserved. Immich group modified state compares the current unique member ID set (ignoring order) and COVER against the immutable original member IDs and primary. Exact restoration clears modified and returns the translated IMMICH indicator to green; remaining differences show yellow. After each editing action, a non-Immich group with an exact original member set regains the missing Immich lineage only when one snapshot matches and that lineage has no active owner. Partial/superset matches, duplicate IDs and ambiguous snapshots do not restore lineage. Its local UI ID and current COVER remain unchanged. Existing Add/Purge/manual-creation operations remain local. Group Purge or dissolution below two members removes the editable group but retains its original state in `sourceGroups`, allowing later unchanged/update/delete/create classification. Re-detection refreshes both membership and auto detection, with the existing confirmation on modified drafts. Editing starts only after resolution and detection complete; resolve errors block editing and never expose selected representatives as ordinary unmatched assets. Editing remains local until the user confirms Send to Immich.

| --- | --- | --- |

Draft IDs are UI-only, distinct from Immich IDs. |

The header and control bar stay outside the content scroll container. Re-detection reads the existing detail API; optional malformed GPS is omitted without failing the photo. Manual draft group creation, Purge, Add, and COVER changes are local only. Modified drafts require a Cancel-first confirmation dialog before re-detection. Stack Add uses the registered unmodified A command; Escape is local page dismissal. Both follow the page shortcut guards. DnD, draft persistence, and Stack Undo/Redo remain unimplemented.

### Stack write workflow

`buildStackWritePlan` classifies current editable groups against uncompleted immutable source snapshots, using unique member ID sets and primary equality rather than edit history or indicator classes. Existing identical Stacks are unchanged (no API call); changed Immich groups are updates; missing Immich lineages are deletes; auto/manual groups are creates. A native confirmation dialog shows create/update/dissolve counts, focuses Cancel and isolates shortcuts. Sending disables draft editing and re-detection; a synchronous request ref prevents double submission. Home navigation remains available. Unmount aborts only the frontend wait, without retrying or assuming that upstream writes stopped.

Backend `POST /stacks/apply` accepts explicit correlated operations. Validation forbids extra fields, invalid UUIDs, fewer than two or duplicate final members, non-member primaries, duplicate operation IDs, conflicting Stack operations and shared assets across final create/update memberships. Limits are 500 operations and 1,000 members per operation; empty requests do no upstream I/O. The frontend exposes the same limits before sending.

The contract is verified against Immich v3.2.4 [Stack DTOs](https://github.com/immich-app/immich/blob/v3.2.4/server/src/dtos/stack.dto.ts), [controller](https://github.com/immich-app/immich/blob/v3.2.4/server/src/controllers/stack.controller.ts) and [repository](https://github.com/immich-app/immich/blob/v3.2.4/server/src/repositories/stack.repository.ts). POST `/api/stacks` accepts `assetIds`, with COVER first, and returns 201 with a Stack. PUT `/api/stacks/{id}` accepts only `primaryAssetId`, returning 200 with a Stack; membership changes therefore release the old Stack through DELETE and create its replacement with a new ID. DELETE returns 204. Successful create/update responses require valid Stack/member IDs, unique matching member sets and the requested primary, independently of response ordering. Malformed success responses are outcome unknown, not safe-to-retry failures.

The executor preloads current upstream membership and rejects missing update/delete targets. All deletes and membership-changing update releases occur before final PUT/POST calls, including membership cycles. Because Immich create can merge entire Stacks when including their primaries, any final operation with members still owned by an unreleased Stack is blocked. Independent operations continue. There is no automatic retry, rollback, cross-call transaction or invented revision lock; concurrent upstream changes after the preflight read remain possible. Client URL construction, API-key headers, timeouts, `trust_env=False`, redirect refusal and sanitized errors follow the existing boundary.

Results distinguish success, failed, unknown and blocked per operation. `releasedStackId` records a committed delete even if replacement fails. The reducer's result action removes successful/unchanged groups without returning their members to unmatched; unrelated unmatched and unused released members stay available for further editing. Failed deletes keep their source snapshot and a labelled pending-dissolution status row. Failed/blocked groups have red accessible status indicators and may be explicitly resent. Unknown results also remain visible, explicitly describe uncertainty and block all sends until re-detection. A lost/malformed backend response conservatively marks outstanding operations unknown.

| State | Owner | Meaning and invariant |
| --- | --- | --- |
| `completedSourceIds` | Editable draft reducer | Retires confirmed or successfully applied source work while preserving the original `sourceGroups` array identity. Retired snapshots cannot regenerate deletes or restore old lineage. A replaced restored group can retain its local UI ID independently of its original snapshot ID. |
| `writeResults` | Editable draft reducer | Correlated per-operation status; delete failures remain retryable even without a current group. A committed replacement release converts remaining work to MANUAL/create, so retry does not repeat deletion of the old Stack. Unknown outcomes survive local editing until reset/re-detection. |
| Send controller/ref and status | Stack page | One active request, localized live status, no request loop or background queue. Requests capture the confirmed plan; editing is disabled until results are applied. |

User-triggered re-detection calls read-only `POST /stacks/refresh` with the original selected asset IDs (at most 1,000), rather than stale route Stack IDs. It resolves current full membership after create/delete/replacement, removes stale selected Stack metadata from auto inputs and rebuilds the source after both loaders complete. Sending never changes route/Home selection, auto-re-detects, resets the page or navigates away. Stack persistence and Undo/Redo are not added.

### Keyboard command architecture

`frontend/src/editShortcuts.ts` is the central registry for application command bindings. Its `shortcutBindings` registry maps the `ShortcutId` union to declarative key/code and modifier definitions. `matchesShortcut()` matches a command including its modifiers; `matchesShortcutKey()` matches the physical/logical key without requiring the original modifiers, as needed for release handling. The registry owns command identity and binding matching, while Home, Anshitsu, ImageViewer, Filmstrip, ScopePanel, and other feature owners keep their own listeners, action execution, availability, and state. GenzoRoom does not use a monolithic global shortcut dispatcher.

`frontend/src/shortcutModifiers.ts` resolves logical Primary and Alternate modifiers for the current platform and provides the shared Primary-modifier check for modified pointer actions. Primary is Ctrl on Windows/Linux and Command on macOS; Alternate is Alt on Windows/Linux and Option on macOS. Registry matching and display formatting use this same resolution. Bindings that require a physical Ctrl, Meta, or Alt remain explicit exceptions; a logical Primary binding rejects the opposite physical modifier rather than accepting Ctrl+Meta together. AltGraph remains excluded where required.

Callers apply the guards appropriate to their command, such as already handled events, IME composition, repeated keys, native editing targets, open dialogs or menus, and disabled, blocked, switching, or saving states. Native and local UI behavior—Tab navigation, Escape, Enter / Space, slider arrows, component focus navigation, and native form editing—is separate from application commands.

`frontend/src/shortcutDisplay.ts` formats human-readable labels from `shortcutBindings`; components do not maintain a second copy of binding strings. It formats arrows, physical Backslash, and Numpad codes for display, and shows multiple bindings such as Redo together. Primary displays as Ctrl on other platforms and ⌘ on macOS; Alternate displays as Alt and ⌥ respectively. Shift matching uses the same `shiftKey` semantics on every platform, while its label is Shift on other platforms and ⇧ on macOS. This is a display-only difference and does not change matching. Explicitly physical modifier bindings retain their physical labels. `useShortcutDisplay.ts` applies the `showKeyboardShortcuts` preference to Tooltip and Menu explanations without changing command matching or action availability. Tooltips retain their normal description when shortcut labels are off, and Menu items remain present without their shortcut labels. Tooltips distinguish held Before from the persistent Before / After button and describe Shift+Z (⇧+Z on macOS) as a Fit / previous-transform toggle rather than the Fit button action.

Current commands include Home `D` (open the current selection, or resume the last Anshitsu workspace when nothing is selected) and Anshitsu `H` (use the existing save-and-return flow), `F` (toggle Viewer focus mode without changing panel state), and `Shift+Z` (displayed as ⇧+Z on macOS; toggles Fit and the previous zoom/pan transform). Filmstrip asset movement uses Primary+Shift+ArrowLeft / Primary+Shift+ArrowRight as a workspace command independent of hover or focus (⌘+⇧+←/→ on macOS). Viewer `]` toggles Preview / Original, and physical Backslash holds Before; the `]` comparison is checked first for JIS keyboard events that can match both. Undo / Redo use Primary+Z, Primary+Shift+Z, and Primary+Y (⌘+Z, ⌘+⇧+Z, ⌘+Y on macOS). Edit-settings copy/paste uses Primary+C / Primary+V, with Primary+Alternate+C / Primary+Alternate+V for selected values. Scope uses Numpad 1–3 for RGB, Numpad 0 for Y Only, and Numpad Decimal for scale; these are physical `code` bindings, not top-row digits or Period.

Anshitsu navigation resume is held only in a module-level in-memory store for the current SPA session; it uses no Storage API and is lost on reload. When the app actually returns to Home, Anshitsu records the valid `WorkspaceNavigationState`: `selectedAssets` in Filmstrip order, current `activeAssetId`, and the Home return context. On Home, a current selection always takes priority for `D`; otherwise `D` resumes that workspace and replaces its `homeReturn` with the current Home context. The store does not retain Recipe, History, Viewer transform, or other transient Viewer and panel state.

Anshitsu derives one workspace keyboard-availability state from Settings, open dialogs and menus, switching, exit saving, and failed switch or exit saves. H / F, Viewer, Filmstrip, Scope, and the `useAssetEdits` Undo / Redo listener receive the relevant blocked state from the workspace owner. In particular, a save-failure alertdialog blocks Undo / Redo so it cannot change the Recipe or History behind the dialog; closing the dialog restores normal shortcut handling.

The backend exposes `/assets/recent`, `/assets/favorites`, `/albums`, `/albums/{id}/assets`, `/calendar/heatmap`, `/calendar/min-year`, and `/calendar/{date}/assets` for Home browsing. Immich credentials and upstream requests remain backend-only. `/assets/edit-status` batches edit-status reads, while `/assets/{id}/edit-state` reads and writes GenzoRoom edit state in SQLite. Album asset visibility follows the existing album search behavior; Timeline visibility filters apply to Recent, Favorites, and Calendar. The shared grid opens selected photos in Anshitsu. The desktop workspace keeps History and EXIF in the independently collapsible left reference panel, places Scope above Develop controls in the independently collapsible right panel, and extends the right panel to the bottom edge. The Filmstrip occupies the lower row below the left panel and Viewer; when the right panel is closed, it spans the full workspace width. JPEG adjustments run locally in the browser.

Anshitsu is desktop-first because practical photo development requires adequate space for the Viewer, Scope, Develop controls, and Filmstrip. Narrow layouts should remain usable enough to avoid critical breakage, but a dedicated mobile development workspace, or a Drawer, Tab, or vertically stacked redesign, is outside the current architecture unless explicitly planned separately. Possible future mobile workflows such as asset selection, stack management, preset application, or sending completed results to Immich should be treated separately from the full Anshitsu editing interface.

The frontend image builds static assets using Vite and TypeScript with Node.js 24, then serves them with nginx. No Node.js or Vite development server runs in the final frontend image. nginx strips the `/api/` prefix before forwarding to `backend:8000`; the browser never connects directly to port 8000. Docker DNS resolution is refreshed so a recreated backend can be found again.

The backend uses Python 3.13, FastAPI, Uvicorn, and HTTPX. `GET /immich/status` calls the stable Immich `GET /api/users/me` endpoint. `GET /immich/about` calls `GET /api/server/about` and returns only `version`, `build`, and `sourceRef` when they are valid strings (each limited to 200 characters), or a safe `error_code`; it never proxies the raw upstream response. Settings treats this optional request independently from photo browsing and the Immich connection status. `GET /assets/recent` calls stable `POST /api/search/metadata`, filters for `IMAGE`, orders by `fileCreatedAt` descending, limits the result to 100, and returns the metadata needed by the grid. `GET /assets/{id}` returns selected non-GPS details and EXIF data. The thumbnail and preview routes proxy Immich-generated images at the corresponding sizes. All Immich calls use the official `x-api-key` header from backend environment variables. The key needs `user.read`, `asset.read`, `asset.view`, `asset.download`, and `server.about`; no write endpoint is used. The JPEG original route validates asset format and response content type, then streams the official `GET /api/assets/{id}/original` response in 64 KiB chunks. It disables nginx buffering through `X-Accel-Buffering: no`, uses private no-store caching, and closes upstream resources on completion, failure, or client disconnect. The original route retains the existing timeout and redirect policy. A failure after response headers terminates the transfer rather than returning a JSON error inside the JPEG. Redirects are not followed, TLS verification remains enabled, and requests use a three-second connect timeout and five-second HTTPX operation timeout; this is not a total download deadline. There are no retries.

Application code uses only the configured `IMMICH_URL`; it does not know whether Docker DNS, a LAN route, or HTTPS provides the route. Selecting and operating that route is a deployment responsibility.

The status response distinguishes missing URL, missing key, unreachable server, rejected or insufficient credentials, and unexpected API responses using safe error codes and messages. Asset endpoints also return only generic configuration, reachability, authentication, or upstream-response errors. They do not return the upstream response body, URL, API key, or internal exception text. The frontend intentionally reduces these details to concise user-facing states.

For optional local development, Vite provides the same `/api/` prefix mapping to a loopback backend. This is separate from the production nginx configuration.

## Shared Settings and browser preferences

`frontend/src/App.tsx` wraps the routed application in `SettingsProvider` from `SettingsDialog.tsx`. Home and Anshitsu render the same `SettingsButton`; the provider mounts the modal alongside the routes rather than replacing a route. Opening or closing Settings therefore leaves the Anshitsu component tree, active edit session, History and cursor, Filmstrip selection, and autosave timer mounted. Settings preferences use a separate browser `localStorage` layer and the external-store subscription in `appSettings.ts`; storage exceptions fall back to in-memory choices for the current session. These preferences do not enter Recipe, History, SQLite edit snapshots, or image processing versioning.

The `showKeyboardShortcuts` preference uses `genzoroom.showKeyboardShortcuts` and defaults to ON. Its `BinaryRadioChoice` presents ON / OFF as grouped native radios. It controls only explanatory shortcut labels: shortcuts remain active when OFF, ordinary Tooltip descriptions remain, and Menu actions remain available. The preference is separate from Recipe, History, and SQLite edit state.

Display language reuses the legacy `genzoroom.language` key. Stored `en` or `ja` values remain manual choices; absent or `auto` values follow `navigator.languages` in priority order, matching primary subtags against the keys of `LANGUAGE_RESOURCES`. The first supported language wins and English is the fallback. Translation resources are enumerated from that map, so later language resources can be added without changing the preference model. `changeAppLanguage()` stores the selected preference, including `auto`, while changing the active i18next language.

Date and time formatting is independent of display language. `genzoroom.dateLocale` stores an explicit supported locale or defaults to `auto`; `resolveDateLocale()` uses the first browser language accepted by `Intl.DateTimeFormat`, then the runtime's default locale. `formatPhotoDate()` is used by Home photo cards and Anshitsu date and EXIF displays. It uses `Intl.DateTimeFormat` date/time styles and preserves the wall-clock fields of timezone-less EXIF values by parsing and formatting those values in UTC; it does not assign the browser time zone to such capture times. Explicitly zoned values continue through normal browser-local formatting. The browser's time zone is not user-configurable here.

`genzoroom.weekStart` independently stores `auto`, `sunday`, or `monday`. `resolveWeekStart()` returns JavaScript weekday numbering (Sunday `0` through Saturday `6`); Auto uses `Intl.Locale.getWeekInfo()` or `weekInfo` when available, mapping ISO Sunday `7` to `0`. Older environments use a deterministic region fallback (Sunday for US, CA, JP, CN, KR, TW, PH; Monday otherwise). Home Calendar uses this resolved value for both month and year views.

WebGPU retains the existing `genzoroom.webgpu.enabled` key and defaults to enabled unless its value is the literal `false`. The Settings switch reports this saved preference separately from runtime availability and actual GPU drawing. Anshitsu owns `useWorkspaceGpu`; unsupported, failed, or disabled GPU processing uses the existing CPU Worker, then the existing main-thread fallback if the Worker fails. GPU active is reported only after an accepted GPU-rendered Canvas result. Home performs a full pipeline availability probe, then immediately disposes it, and does not retain a processing renderer. Settings changes are subscribed live by the workspace and do not remount it.

`genzoroom.initialImage` stores `auto`, `original`, or `preview`, with `auto` as the default. `prefersOriginal()` resolves Auto to Original only while GPU processing is enabled and available. `useJpegOriginal()` displays the existing preview during its active-photo JPEG request; when an original is ready, Auto or Original preferred selects it. Preview preferred never promotes automatically. A per-photo manual Preview / Original choice is marked manual and takes precedence over later readiness or GPU-state changes. Changing photos resets that photo-specific choice; the existing abort and object-URL release path prevents an old request from replacing or retaining the new photo's source. The preference is not added to recipes or persisted edit state, and Home does not fetch originals.

`SettingsDialog` uses a native modal `<dialog>` with `aria-modal` and a labelled heading, initial focus, Tab / Shift+Tab trapping, Escape and close-button handling, and focus restoration to the opener. Backdrop dismissal requires a primary pointer press and release both outside the dialog bounds, so an inside-originating drag cannot dismiss it. Pointer events are contained, and capture-phase window key handlers suppress background shortcuts while the dialog is open; Anshitsu also blocks its viewer/edit shortcuts for the open interval. Closing the modal does not invoke edit, History, or save operations.

The dialog requests `/api/health`, `/api/immich/status`, and `/api/immich/about` independently, with bounded requests and a manual refresh. The latter is proxied by nginx to backend `GET /immich/about`; `get_immich_about()` reads credentials only from backend environment variables and calls Immich `GET /api/server/about`. The response model `ImmichAbout` exposes only `version`, `build`, `sourceRef`, or a safe error code. The API key is never returned to or stored by the frontend. Immich API keys need the `server.about` permission for the optional server information; permission or network failures do not disable existing photo or edit APIs. Home's compact connection status remains in place.

The Settings implementation and follow-up layout/backdrop changes do not alter Recipe v18, History, SQLite schema version 1, or `processingVersion` (`jpeg-preview-srgb8-v1`).

## Docker deployment

`docker-compose.yml` defines two services:

| Service | Container port | Host exposure | Role |
| --- | --- | --- | --- |
| `frontend` | `8080` | `${GENZOROOM_PORT:-3190}` | Static file serving and API proxying. |
| `backend` | `8000` | None | Immich proxying and SQLite edit-state API. |

Only the frontend publishes a host port. Both services join a project-scoped `api` network marked `internal: true`. The frontend also joins a `web` bridge network for its published entry point, while the backend joins a separate `outbound` bridge network for LAN, routed, and HTTPS connections. Joining `outbound` does not publish backend port 8000. The backend bind-mounts one host data directory at `/data`; no host networking, GPU, or privileged mode is used.

The standard `docker-compose.yml` has no dependency on an Immich Docker network. The optional `docker-compose.immich-network.yml` attaches only the backend to an existing external network selected with `IMMICH_DOCKER_NETWORK`. This enables Docker DNS access to an Immich service on the same host without exposing the backend or attaching the frontend to Immich. The external network and Immich service name belong to the deployment environment and are never hardcoded by GenzoRoom. The application still receives only `IMMICH_URL` and `IMMICH_API_KEY`; `IMMICH_DOCKER_NETWORK` is consumed by Compose.

Both containers run as non-root users, drop Linux capabilities, and disable privilege escalation. The backend runs as UID/GID 10001:10001 and requires a writable host data directory. `.env` provides Compose inputs for the host port, Immich connection, and persistence root, but it is not mounted into the application; Portainer can supply the same values through stack environment variables.

Compose starts the backend before the frontend but does not wait for API readiness. Startup failures are visible in container logs and the UI; the user can check again after services become ready. Both services use `restart: unless-stopped`.

The files support builds on a Docker host with Docker Compose. When Portainer is used, a Git Repository stack can use `docker-compose.yml` as its Compose path and, when same-host networking is needed, `docker-compose.immich-network.yml` as an additional path. Portainer must target the Docker endpoint where the external network already exists. The configuration does not provide prebuilt registry images or Swarm deployment support.

See the [deployment guide](deployment.md) for startup, verification, troubleshooting, and removal commands. Removing the Compose deployment removes its containers and networks; copied deployment files and built images remain until explicitly removed.

## JPEG editing foundation

Anshitsu keeps active edit sessions in an in-memory map keyed by Immich asset ID. Each session contains a JSON-serializable flat Recipe v18, committed history entries (`kind`, `before`, `after`), a history cursor, and an optional pending transaction. The recipe has four category flags, three Color Grading range flags (`gradingShadowsEnabled`, `gradingMidtonesEnabled`, `gradingHighlightsEnabled`), sixteen numeric values, and sixteen per-adjustment `adjustmentEnabled` flags. All 23 flags default to true; numeric values default to zero. Category, range, and individual flags are independent, and disabled values remain stored. Recipe v17 is accepted and migrated when reading legacy saved state. Only JPEG assets are editable. Activating a JPEG normally loads its edit state from SQLite before enabling editing. If an Anshitsu session still holds dirty local edits or an unconfirmed save after a failed exit, reactivating that asset keeps the local state and does not replace it with a GET result; explicitly discarding local state removes the record and requires a fresh GET. Dirty edits are autosaved after five seconds of inactivity, and dirty Filmstrip switches save before navigation. The Home control saves all assets edited during the current Anshitsu session, compacting each History before the final save. Browser Back, page reload, and browser or tab close do not trigger a final save; the debounce interval and in-flight edits may therefore remain unsaved.

| Category | Adjustment keys | Enabled flags |
| --- | --- | --- |
| White Balance | `temperature`, `tint` | `whiteBalanceEnabled` |
| Basic | `exposure`, `contrast`, `highlights`, `whites`, `shadows`, `blacks` | `basicEnabled` |
| Color Grading | `shadowsTemperature`, `shadowsTint`, `midtonesTemperature`, `midtonesTint`, `highlightsTemperature`, `highlightsTint` | `colorGradingEnabled`, plus the three range flags above |
| Color | `vibrance`, `saturation` | `colorEnabled` |

Each adjustment also has its own `adjustmentEnabled.<id>` flag. Category, Color Grading range, and adjustment flags are independently editable and independently represented in History; disabling any level bypasses processing while retaining the stored values.

### Edit clipboard and Paste

`frontend/src/editClipboard.ts` owns one module-memory clipboard per browser tab. It stores a detached copy of selected adjustment values plus the source asset ID and filename; it neither references the live recipe nor reads or writes the OS clipboard. Normal Copy stores all sixteen Recipe v18 adjustment values, selected Copy stores the chosen values, and slider Copy stores one value. All three replace the same clipboard. Copy reads the saved recipe values rather than `effectiveAdjustments`, so disabled categories, ranges, and adjustments still copy their retained numbers. None of the 23 enabled flags is copied. The clipboard survives route changes, Home, and reopening Anshitsu within the tab, but not a page reload or tab close.

The Viewer’s `⋯` menu exposes Copy all, Copy selected, Paste copied, and Paste selected. With the Viewer as the keyboard target, Primary+C copies all values unless the existing slider operation target is active; then it copies that adjustment only. `adjustmentFocus.keyboardAdjustment()` is the shared operation-target source for slider keyboard control, including the active hover or focused range input, so Copy does not maintain a second target. Primary+V applies the clipboard values to the active photo without requiring Viewer or slider focus. It is available after the active photo’s edit state loads and is blocked during photo switching, exit saves, a modal selection, or other non-editable states. Primary+Alternate+C and Primary+Alternate+V open the selection dialog while the Viewer is the keyboard target. Anshitsu’s handlers ignore native text-editing targets, composing IME input, AltGraph, repeats, unsupported modifiers, and already handled events. Dialog events are isolated from the workspace; Escape cancels, Space uses native checkbox toggling, Enter confirms from a checkbox unless the selection is empty or the key is repeating, and focused buttons keep their native Enter action. The modal dialog traps Tab navigation and restores the prior connected focus on close. The menu is an alternate entry point when the Viewer is not focused.

Selected Copy starts with all sixteen items checked. The shared dialog groups items under White Balance, Basic, Color, and Color Grading; Color Grading separates Shadows, Midtones, and Highlights. It supports individual and category selection, indeterminate category state, and all-select / clear-all controls. Selected Paste offers only clipboard items and checks every candidate, including values equal to zero; deselected values are omitted from that Paste without changing the clipboard. No empty selection can be confirmed. Items are shared from the recipe’s `ADJUSTMENT_IDS` and category definitions. The Paste reducer applies only the supplied adjustment IDs in one edit action and leaves all 23 destination enabled flags intact. It commits any pending slider edit first and creates one compound History entry only when a value changes. A no-op Paste creates no Paste entry and does not itself discard Redo; a pending slider operation is still committed separately before Paste.

A Paste entry has `kind: 'paste'`, complete Recipe `before` and `after` snapshots, and metadata `{ sourceAssetId, sourceFilename, adjustmentIds }`. The source filename is shown in History. Undo and Redo replay the compound recipes. History compaction processes applied and Redo branches independently and explicitly keeps Paste entries separate from adjacent operations. Clipboard state is transient; Paste itself follows the ordinary edit dispatch, dirty detection, autosave, Filmstrip save, and Home-exit save/compaction paths.

The frontend defines persistence snapshots in `frontend/src/editState.ts` and normally loads them through the edit-state API when a JPEG asset is activated. Snapshot `stateFormatVersion` 2 is independent of Recipe v18 (with v17 read compatibility), SQLite schema version 1, and `jpeg-preview-srgb8-v1` processing version. A snapshot contains the current recipe, full History and cursor, and Immich preview source identity. Creating one commits pending work on a copied session, leaving the live editing gesture unchanged. Frontend and Backend validation reject unsupported versions, malformed recipes or entries, kind/diff mismatches, broken History continuity, and a cursor/current-recipe mismatch without replacing or discarding data. A Paste entry requires exactly typed source asset and filename metadata plus a non-empty, duplicate-free list of known adjustment IDs. Its before / after recipes must be valid, all enabled flags must match, at least one numeric adjustment must change, and every changed adjustment must appear in the metadata list. The validators allow strictly validated v1 snapshots for read compatibility; snapshot v1 uses the legacy History entry form and cannot contain Paste. Reading v1 does not rewrite the database. The next changed save emits a validated v2 snapshot. Paste metadata and semantics are accepted only for v2. A rollback to a release that only understands snapshot v1 may therefore fail to load an asset after a v2 snapshot has been saved. History kinds remain an explicit supported set; unknown future kinds are rejected rather than preserved as opaque entries.

Pure History compaction processes the applied and Redo branches independently, preserves the current recipe, and recalculates the cursor. Consecutive operations on one numeric adjustment or one enabled flag collapse to their first before / last after; a round trip disappears. If a run disappears, newly adjacent matching operations are considered again. Supported Reset kinds and Paste entries stay independent. `COMPACT_HISTORY_ON_EXIT` defaults to true; autosaves and Filmstrip saves use uncompressed History, while the Anshitsu Home exit compacts all session-edited assets.

`useAssetEdits.organizeHistory()` exposes `clearHistory`, `trimHistory`, `resetEdits`, and manual `compactHistory` for the History menus. Clear, trim, and manual compaction retain a deep copy of the previous EditSession only when History actually changes. The next Undo, through either the button or shortcut dispatch, restores that complete session including Recipe, Redo, cursor, and pending work, then consumes the backup. `canUndo` includes this restoration right even at cursor zero; `hasOrganizationUndo` identifies it separately. Reset has no organization Undo.

Any subsequent user edit intent (including a no-op value, Paste, Redo, or History jump), reset, or another organization attempt consumes the previous backup. A successful changed organization replaces it; a no-op or failed attempt creates none. Compaction failure leaves the live session intact. Internal commit callbacks, focus changes, rerenders, autosave, and save responses retain the backup. Photo navigation and Home exit discard it. Backups are transient per-photo records and never appear in snapshots or SQLite. Restoring after a save uses the ordinary dirty detection and save path to write a new revision; unknown PUT results are still resolved with the original request first. Save responses synchronize a compacted live session only if both its session object and fingerprint still match the request's original live state.

History's header menu offers compact, clear, and reset; row context menus additionally offer partial deletion at the invoked row. Both use the same operation definitions and `organizeHistory()` handlers. Right-click or Shift+F10 opens a row menu without jumping. An explicit trim cursor deletes the clicked row and earlier operations atomically: if the live cursor is newer, the live Recipe and pending work remain and the cursor decreases by the removed count; if older, the selected row's after Recipe becomes the starting point at cursor zero and replaces the pending preview. Organization Undo restores the entire original session including that pending work. Initial State's context menu uses the live cursor, with trim disabled at zero. Menus are portaled into a fixed viewport-clamped overlay and close on selection, Escape, Tab, outside pointer action, or photo navigation.

Clear and reset use a native `dialog.showModal()` confirmation with localized Japanese Cancel / Continue (`キャンセル`／`続行`) and English Cancel / Continue buttons. Cancel initially receives focus; its focused state is red and Continue's is gray. Tab/Shift+Tab cycles buttons, Enter activates the focused button, Y continues, and N or Escape cancels. Only reset shows a warning icon and the message “この操作は元に戻せません。” / “This action cannot be undone.”; clear can be recovered by the organization Undo. IME, AltGraph, repeats, handled events, and modified Y/N input are rejected. The modal isolates background keyboard events, prevents other History and clipboard actions, and restores the invoking focus after it is re-enabled. Confirmation is bound to the original asset ID and rechecks edit availability at Continue. Compaction failures show an alert outside History; success adds no explanatory text. Persistence formats and save behavior are unchanged.

Increment `processingVersion` only when the intended output pixels for the same recipe change, such as a gain formula, Color Grading weight, stage order, or color-space meaning. UI, History, storage changes, byte-identical optimizations, and Worker implementation changes do not increment it.

Individual adjustment Reset changes only its value and preserves that adjustment's enabled flag. Color Grading Reset changes its six values in one History operation and preserves the parent, range, and individual flags. All Reset restores all sixteen values and all 23 flags. Individual, category, and range toggles commit pending adjustment edits first, then commit one separate History operation without changing numeric values. Parent categories may be off while child switches change; child settings take effect when their parent is enabled again.

`editing.ts` provides pure begin/update/commit/reset/undo/redo transitions. Preview changes use the current recipe immediately. Pointer release/cancel, control unmount, or 500 ms keyboard/wheel inactivity commits one operation. Keyboard input resets the timer on every accepted keydown; keyup, pointer leave, and focus changes do not commit it early. No-op operations compare the complete recipe, including all 23 enabled flags and sixteen adjustment values, and do not create history or discard redo. A new committed edit after Undo replaces the redo branch. History rows are keyboard-accessible jump buttons; selecting a row restores the recipe after that operation while retaining the Redo branch, and the trailing Initial State row restores the recipe before the first operation. A jump commits pending slider work first and records no new History entry. Each adjustment Reset, individual/category/range toggle, category Reset, and All Reset has a separate operation kind; all are undoable. Category and adjustment resets affect only their own values and preserve enabled flags. All Reset restores all sixteen values and all 23 enabled flags to defaults in one operation. Their History labels stay concise and are localized at display time rather than stored in recipes. The flat in-memory recipe schema is version 18; durable snapshots retain the recipe, full History, and Undo/Redo cursor in SQLite.

`AdjustmentSlider` supplies a compact reusable adjustment row with its label, native range input, synchronized direct numeric input, optional fixed-width unit slot, and inline reset in one responsive grid row. The label truncates when necessary while the range column consumes the remaining sidebar width. Direct input updates the current recipe only for finite normalized values, commits on Enter or blur, and restores its pre-edit value on Escape or invalid input. `editShortcuts.ts` protects text and number inputs, textarea, select, contenteditable, and IME input from the hover/focus slider shortcuts. Focused other sliders retain their own behavior. Exposure is bounded to −5…+5 EV in 0.01 EV increments with two displayed decimal places; every other current adjustment uses −100…+100 integer steps. Temperature and Tint controls use their corresponding directional gradient tracks. Color Grading controls are ordered Shadows Temperature/Tint, Midtones Temperature/Tint, Highlights Temperature/Tint; each group header has a compact ON/OFF button that disables only its two sliders while preserving their values. Vibrance and Saturation use normal tracks with no unit. The categories appear as White Balance, Basic, Color, then Color Grading; this display order is independent from the pixel pipeline order. Each category’s expanded state is local UI state that starts expanded on every Anshitsu entry and is not persisted. When a category is disabled, only its controls are disabled and dimmed while its values remain intact; only that category’s adjustments are bypassed. The temporary-preview notice remains outside the collapsible categories.

### Anshitsu component boundaries

`AnshitsuPage.tsx` composes the workspace and owns page-level photo navigation, edit-session actions, menus, and data handoff. `Filmstrip.tsx` owns thumbnail presentation and active-item scrolling; its registered Primary+Shift+Arrow commands activate adjacent assets without hover/focus-dependent navigation or focus transfer. `WorkspaceLayout.tsx` owns the two panel widths, `ResizeObserver`, resize handles, and remembered-width persistence while retaining the workspace DOM structure and CSS variables. `EditHistory.tsx` renders the supplied History and cursor and reports row selection or context-menu requests through callbacks; it does not perform History operations.

`adjustmentFocus.ts` owns the mounted-slider registry, shared operation target, keyboard-versus-pointer ownership, and focus transfer/restoration functions used by `AdjustmentSlider`, Anshitsu, Color Grading controls, and the Viewer. `AdjustmentSlider.tsx` retains each control’s numeric input, pointer, wheel, edit-commit handling, and existing per-control event listeners. `adjustmentNavigation.ts` supplies DOM destination and scroll helpers, while `editShortcuts.ts` retains key classification and native-input guards. The shared focus module does not import the slider component, so the dependency boundary has no reverse cycle.

`useAssetEdits.ts` remains the owner of per-asset edit sessions, state loading and saving, retry/autosave sequencing, and exit-time History compaction. These operations continue to share session state and ordering; the structural review left the hook intact. `ScopeResizeHandle.tsx` controls the Scope/Develop divider, while `scopeSizing.ts` independently reads and writes the Scope height under its own localStorage key. The default is 30%; restored values below 15% or malformed values use the default, and values above 40% are capped at 40%. Dragging commits on pointer release, and keyboard resizing commits on each supported key. The selected height persists across Anshitsu visits and photo switches, independently of the remembered sidebar widths. Narrow layouts hide the divider and retain the vertically stacked workspace and sticky Filmstrip.

The current rendering path is:

```text
Selected preview or cached JPEG original adapter (editImageSource.ts)
  → browser decode into sRGB RGBA
  → adjustmentWorkerClient.ts (one source copy transferred on initialization; recipes sent per render)
  → adjustmentWorker.ts → adjustmentWorkerRuntime.ts
  → adjustmentPipeline.ts (immutable source → linear-light Temperature → linear-light Tint → linear-light Exposure gain 2^EV → sRGB midpoint Contrast → Highlights → Whites → Shadows → Blacks → masked linear-light Shadows Temperature → masked linear-light Shadows Tint → masked linear-light Midtones Temperature → masked linear-light Midtones Tint → masked linear-light Highlights Temperature → masked linear-light Highlights Tint → Vibrance → Saturation)
  → result buffer transferred to AdjustedImage.tsx → adjusted Canvas → existing Viewer transforms

Decoded source pixels → unadjusted Canvas in the same Viewer position
```

`effectiveAdjustments` substitutes defaults for each disabled category, individual adjustment, and (when Color Grading is enabled) disabled Shadows, Midtones, or Highlights pair. The source recipe retains all numeric values and flags. A disabled individual adjustment becomes its default value; a disabled range bypasses its pair; a disabled category bypasses its full group. These switches do not alter one another. Color Grading Reset clears only its six values; All Reset also turns all 23 flags back on.

The no-op check considers all sixteen effective values and returns exact source bytes when they are zero. Alpha is preserved. Existing White Balance and Basic tone formulas, luminance-region skips, intermediate rounding, and stage order are unchanged. The three Color Grading pairs run after Blacks with the shared weights and gains described below; each active stage clips and rounds before the next.

Vibrance runs after Highlights Tint. It uses `Y = 0.2126R + 0.7152G + 0.0722B`, `chroma = max(|R−Y|, |G−Y|, |B−Y|)`, and `lowSatWeight = 1 − clamp(chroma / 0.5, 0, 1)`. Positive strength is `0.75 × lowSatWeight`; negative strength is `0.6 × (0.25 + 0.75 × lowSatWeight)`. With `factor = 1 + vibrance / 100 × strength`, each channel becomes `clamp(Y + (C−Y) × factor, 0, 1)` and is rounded to 8-bit before Saturation. Zero-valued stages are skipped. Every render starts from the untouched decoded source, so edits do not accumulate clipping from previous renders.

This remains an 8-bit sRGB processing pipeline. Home and Filmstrip use Immich thumbnails. Anshitsu initially displays the Immich preview and acquires only the selected JPEG original in the background, while preview editing continues. JPEG-only captures and Pixel `RAW-01.COVER.jpg` use the same filename-format classification; DNG and other formats have no original acquisition. The compressed original is reused while the asset remains selected and released on navigation or unmount; it is not cached across the Filmstrip. Preview / Original is local display state alongside Before / After and never changes Recipe, History, sourceIdentity, saved-data versions, or SQLite. Both sources receive the same current recipe, including all bypass flags, Undo and Redo. Viewer 1:1 uses the dimensions of the displayed source; switching sources resets zoom/pan to Fit.

JPEG originals decode only when selected for display. An HTML image retains embedded ICC interpretation; drawing into an explicitly verified sRGB Canvas and reading sRGB ImageData performs browser-managed conversion before pixel processing. Display P3 is not relabeled as sRGB. Out-of-sRGB colors are limited by the existing 8-bit working space. No RAW, wide-gamut, HDR, export, or special original-processing interlock is introduced. NAS / Firefox checks confirmed sRGB and Display P3 appearance by visual inspection, not color-difference measurement. Before WebGPU was introduced, repeated adjustment updates on the tested setup using the CPU pipeline took about two to three seconds by user estimate; this was an acceptance observation, not a benchmark, and does not describe current WebGPU performance.

Immich's Asset EXIF response has no ICC profile description field. `jpegProfile.ts` reads bounded JPEG metadata slices from the already-acquired original, assembles ICC APP2 segments, and reads v2 desc or v4 mluc profile descriptions. It does not use EXIF ColorSpace or assume sRGB. Missing ICC and unknown/malformed metadata are displayed separately. The left metadata panel is labelled “Original Info” / “原版情報”; its profile and image dimensions are original-derived and remain visible in either display mode. Profile descriptions do not determine pixel transforms.

| --- | --- | --- |

Original transfer or decode failure leaves preview editing available. Mode toggles do not refetch the current original. Revisiting a different photo may fetch it again because original memory is released on navigation. The top Viewer switches are ordered Preview / Original, then Before / After; the left History and right Develop panel controls use directional arrow icons and localized tooltips. `]` toggles Preview / Original and Backslash temporarily displays Before while held. The `]` character check precedes the Backslash physical-key check, so JIS `key: "]"`, `code: "Backslash"` toggles the source without activating temporary Before. Acquisition-not-ready states suppress that shortcut action. Existing native-input, IME, dialog, and menu guards apply.

### Color Grading weights and shared gains

Let `S(a,b,Y) = x²(3−2x)`, where `x = clamp((Y−a)/(b−a), 0, 1)`. Here Y is calculated from normalized **sRGB bytes**, not linear-light RGB. Each range calculates Y once before its Temperature stage and shares the resulting weight with its Tint stage. The next range uses the rounded output of the preceding range.

| Range | Weight | Full strength | Transition |
| --- | --- | --- | --- |
| Shadows | `1 − S(0.15,0.35,Y)` | Y ≤ 0.15 | Fade out 0.15–0.35; zero from 0.35 |
| Midtones | `S(0.15,0.35,Y) × (1 − S(0.60,0.78,Y))` | 0.35–0.60 | Fade in 0.15–0.35; fade out 0.60–0.78 |
| Highlights | `S(0.55,0.75,Y)` | Y ≥ 0.75 | Zero through 0.55; fade in 0.55–0.75 |

Temperature targets are `(1.5^−t, 1, 1.5^t)` with `t = value/100`; Tint targets are `(1.3^u, 1.3^−u, 1.3^u)` with `u = value/100`. Each range applies `targetGain^weight` in linear RGB. Each active stage clips, encodes, and rounds separately. All ranges use the same channel-gain helper and module-level 256-entry Float64 sRGB decode table. Global Tint shares one LUT for its identical red/blue gains; weighted Tint calculates their identical effective gain once per pixel. These are exact reuse operations, not approximations or stage fusion.

Range thresholds are named constants in three pure weight helpers. Future Point / Width support can parameterize these helpers, but must first define how shoulder-shaped Shadows/Highlights and the Midtones plateau map to those controls, including edge clamping and valid widths. No Point / Width fields or migration system exist in Recipe v18.

### Worker ownership and limits

`AdjustedImage` decodes the source once and retains its buffer for CPU fallback. The CPU Worker client transfers a single copied source buffer to the Worker when that decoded source changes; recipe messages contain no pixel copies. `adjustmentWorkerRuntime` calls the same pure `renderAdjustments()` used by the main-thread fallback, with the complete v18 recipe. It retains its source and transfers the new output buffer back. There is no separate Worker pixel algorithm or per-adjustment protocol mapping. The GPU renderer is available for JPEG preview and selected-original sources only; other assets continue through the existing image display path.

The Viewer keeps Preview / Original and Before / After as display state outside the recipe and History. `AnshitsuPage` owns the persistent Before / After choice across Filmstrip asset switches; `ImageViewer` owns the temporary held-Backslash state, matched by `KeyboardEvent.code`, and the `]` source toggle. `AdjustedImage` draws decoded input pixels into a Before Canvas and Worker/fallback output into an overlaid After Canvas. Comparison changes only the After Canvas visibility, so it issues no render request and leaves the shared Viewer zoom/pan transform intact. A new source clears the previous canvases before its decode/result is displayed. Before bypasses develop adjustments; future geometric transforms should feed both display paths before this split.

The CPU Worker client permits one in-flight render and one pending latest recipe. When a newer recipe is pending, the completed older output is discarded and the latest request is sent. Worker request IDs and asset generations reject mismatched results. RAF coalesces changes before submission. Decode is aborted on source change/unmount; pending RAF is canceled, Worker callbacks are removed, and the old Worker is terminated. Worker startup, initialization, message, and runtime errors use the retained source in the main-thread fallback. GPU scheduling and its separate fallback path are described below.

Each render still needs one output buffer of `4 × width × height` bytes, including an identity result: transferring the retained source would detach it. Main-thread fallback storage, the Worker's retained source, and the additional Before Canvas backing store for immediate comparison are intentional. Small gain/tone LUTs have 256 entries; there are no full-image per-stage buffers. Stage-specific encode/round/decode boundaries preserve current output and cannot be fused without reconsidering that behavior. Full-size CPU pixel work and Canvas upload remain proportional to pixel count. Worker scheduling improves responsiveness but cannot cancel a render already running or reduce its pixel count; sustained latency may require a separately designed reduced-resolution interaction path. No end-to-end Firefox performance claim is made from unit tests.

The Backend stores the current recipe, full Undo/Redo History and cursor, source identity, four separate version domains, revision, timestamp, and last save ID atomically in one SQLite row per Immich asset. `PRAGMA user_version=1` tracks table structure; later schema migrations can be added sequentially. Connections are opened per operation with WAL, `synchronous=FULL`, and a 3000 ms busy timeout. The GET route returns `{ state: null }` only for an absent row. PUT accepts a validated edit-state snapshot plus `expectedRevision` and UUID `saveId`, returns revision and UTC timestamp, rejects stale revisions, and recognizes an identical retry of the latest save ID. When a network result is unknown, the frontend retains the exact snapshot, expected revision, and save ID and retries that request before sending a newer snapshot. A repeated request that no longer matches the latest DB revision remains a 409 conflict; no automatic merge occurs. Requests are limited to 8 MiB at nginx and Backend. Validation is repeated when reading stored JSON. Invalid payloads return safe 422 codes; unavailable or inconsistent database state returns safe 503 codes without affecting Immich routes. The frontend blocks JPEG edits until GET succeeds, compares snapshots with its last confirmed save, autosaves dirty state after five seconds without an edit, and saves dirty state before Filmstrip navigation. Autosaves and Filmstrip saves preserve full History. The Anshitsu Home control sequentially saves every asset edited in that session, including assets already clean after autosave, and compacts each History before saving. Confirmed compact saves synchronize the live session; partial successes stay committed if a later asset fails. Exit save failures offer stay or exit without saving. Browser Back, reload, and close interception are not implemented. Image write-back is not connected yet.

### WebGPU Recipe renderer (G2) and workspace integration (G3)

`WebGpuAdjustmentRenderer` is shared by `/dev-webgpu.html` and the Anshitsu JPEG Preview / Original paths. G3 selects it through `AdjustedImage`; the G2 arithmetic and WGSL are unchanged. G1's `WebGpuExposureRenderer` and exposure shader remain compatible. Both renderers reuse the same WebGPU availability and error-scope helpers.

`useWorkspaceGpu` owns the initialized renderer and device. It checks Secure Context, the GPU API, adapter, device, and G2 pipeline creation. Missing vendor information is irrelevant. Initialization resources become the drawing resources when ON; an OFF availability probe is disposed immediately. Asset/source changes, preference changes, and unmount abort initialization and dispose the previous renderer. `create()` accepts an optional abort signal and destroys devices returned by an uncancellable late `requestDevice()`. Idle device loss is observed through `onDeviceLost()` as well as rejected render requests.

| G3 state | Owner, update rule, and invariant |
| --- | --- |
| `genzoroom.webgpu.enabled` | `webgpuSettings` reads/writes the browser preference, default ON. Storage failures do not prevent processing. This setting is outside Recipe, History, and saved edits. |
| Availability and renderer lease | `useWorkspaceGpu`, keyed by asset/source and preference. Checking, available, unavailable, and runtime error are distinct. Unavailable/error use CPU without overwriting the saved preference. A new source or workspace entry retries initialization. |
| Actual GPU display status | The workspace reports GPU active only after an accepted Canvas result from the current renderer; a saved ON preference alone is insufficient. |
| GPU source and pending Recipe | `AdjustmentGpuClient`, one upload per client, one running operation and at most one latest pending Recipe. It does not own the device. Client disposal suppresses callbacks; the workspace releases the device. |
| Result acceptance | `AdjustedImage` checks the live source, renderer identity, client lifetime, and Recipe reference, including changes before the next RAF. GPU results also validate source generation and increasing request ID. Worker request/asset checks remain in place. |

GPU initialization, upload, execution, or device-loss failures select the existing CPU Worker; Worker failures retain the main-thread fallback. These changes reuse decoded pixels and never invoke image acquisition, Recipe updates, History changes, or saving. Route/source switches retire old clients, so overlapping photo, Recipe, Preview / Original, and GPU / CPU changes cannot publish a retired result. Canvas and After Histogram are published together from the accepted output; GPU readback uses the existing CPU `collectHistogram()`. Before / After and zoom remain display-only state. No automatic retry loop runs after a runtime failure.

Call `create()` (null on unavailable/initialization failure, with optional error diagnostics), then await `setSource(rgba, width, height)`, and await `render(recipe)` serially. The upload copies the caller's bytes without detaching or retaining the CPU array. Recipe-only changes reuse that single GPU source; another `setSource()` explicitly replaces it, even for the same array object. Concurrent uploads/renders reject with a busy error and are not queued. A failed replacement invalidates the previous source; a failed render releases temporary buffers and rejects so the caller can choose CPU fallback. Device loss and disposal permanently reject further operations. Always call `dispose()` at the end.

| State / resource | Owner and invariant |
| --- | --- |
| Uploaded source and dimensions | Renderer; at most one source buffer, destroyed on replacement, loss, or disposal. |
| `sourceGeneration` | Renderer; increases on each accepted upload attempt, including failures. Results identify their uploaded source generation. |
| `requestId` and prepared Recipe | Renderer; monotonically increasing render IDs and synchronous parameter snapshots. Consumers must retain request/source identity when adding future scheduling; a result is not an implicit latest-state update. |
| Output, readback, uniform and LUT buffers | One render only; released on success or failure. No global device/buffer cache. |

`effectiveAdjustments()` supplies all v18 individual, category, and 3WAY range bypasses. Three 256-entry RGB tables are produced with the unchanged CPU Pipeline: Temperature, Tint, and the existing combined Exposure/Contrast stage. WGSL applies them in that order, preserving each byte boundary rather than approximating global decode/encode on GPU. Four luminance-dependent tone stages, three separately rounded Temperature/Tint grading pairs (with the pair's shared pre-Temperature weight), Vibrance, and Saturation follow in CPU order using f32. CPU-generated grading gains reuse `temperatureGains()` / `tintGains()`. Alpha remains an untouched packed byte. No Recipe or persistence version changes are involved.

Results contain `{ pixels, width, height, sourceGeneration, requestId }`; `pixels` is an independent RGBA `Uint8ClampedArray` and may be passed directly to the existing `collectHistogram()`. Histogram collection is not part of the shader or renderer.

The smoke page uses 512 generated pixels and individual endpoints/representative values, disabled controls/categories/ranges, combined Recipes, and cumulative stage cases. It reports differences without an automatic pixel tolerance. Node tests distinguish lifecycle mocks, a double-precision stage model against CPU, an f32 arithmetic model, and conditional real-GPU execution. Models do not compile WGSL or establish GPU `pow`/contraction accuracy. G2 was hardware-tested in Firefox and Edge: all 114 cases executed, maximum CPU/GPU byte difference was 2 in either browser, alpha matched, and no GPU execution errors occurred. G3's integrated workspace was hardware-tested on the NAS in Firefox. Edge has no reported G3 workspace verification. Mock scheduling tests do not establish real GPU drawing success.

### Developer Diagnostics

`/developer` is a lazy-loaded SPA route intended for opt-in development and diagnosis, not a primary user workflow. An ordinary click on the Settings gear opens Settings as before; a Primary-modifier click opens `/developer` in a new tab, using the shared platform-aware modifier resolver. The new tab is opened synchronously from the click handler to preserve browser popup behavior. Opening the route only reads a passive Environment snapshot and does not fetch photos or initialize WebGPU. Diagnostic runs and manual candidate lookup require explicit actions.

Environment / Capabilities stays visible above the Real JPEG and WebGPU tabs. Both diagnostic components remain mounted while the selected panel changes with `hidden`; tab selection is page-local and is not stored or encoded in the URL. JPEG candidates, manual selection, UI-only filename, JPEG report and WebGPU report therefore survive tab changes. Leaving the route releases each component's resources.

`DeveloperPage` captures one Environment snapshot at mount: secure context, cross-origin isolation, WebGPU API availability, hardware concurrency, device memory, device pixel ratio, viewport dimensions, user agent and platform. Unavailable optional values are `null`. The page does not probe an adapter when it reads availability.

#### Synthetic WebGPU Smoke

The WebGPU tab runs the production `WebGpuAdjustmentRenderer` against generated pixels. It is a synthetic correctness, capability and pipeline diagnostic, not a real-photo performance benchmark. It reports CPU/GPU output comparisons, adapter information, features, limits and timings. Cases cover adjustment values and endpoints, individual adjustment and category OFF behavior, combined adjustments, and stage-prefix outputs. Cases execute serially; a run owns and disposes its renderer/device, suppresses late publications after departure, and releases a device or renderer that arrives after its owner has closed.

#### Real JPEG Diagnostics

Real JPEG Diagnostics reuses `fetchRecentAssets()`, the original endpoint, `readJpegProfile()`, `decodeEditSource()`, `renderAdjustments()`, `WebGpuAdjustmentRenderer` and `collectHistogram()`. Automatic runs inspect at most the 50 newest Recent assets and use the first non-RAW JPEG. The explicit manual chooser displays up to 10 non-RAW JPEG candidates. Selection, candidate data and filename remain transient in the page; the filename is shown only in the UI and is never put in a report or browser storage.

A run fetches the original Blob, reads its ICC/profile description, and uses the production JPEG-original path to decode into sRGB ImageData. It measures the source histogram once, creates one GPU renderer and uploads the source once. It then runs 17 serial cases through the existing CPU and GPU paths: one case for each of the 16 numeric adjustments and `all_sliders_representative`. Each individual case changes only its target value from `defaultRecipe()`; representative values are exposure `0.5` and `35` for all other adjustments. CPU and GPU outputs each receive a separately timed histogram collection. GPU failure retains CPU results and stops additional GPU cases.

#### Timings and reports

Real JPEG timing covers total run and cleanup, automatic asset lookup, original fetch through `response.blob()` completion, profile reading, production decode through sRGB ImageData, source histogram, GPU initialization, one source upload, and per-case CPU render, CPU histogram, GPU render/readback and GPU histogram. Manual selection has no asset-lookup timing. `gpuRenderMs` is the production renderer call through readback and CPU-side pixel copy, not pure shader execution. Initialization includes its adapter/device requests and pipeline creation. Measurements are single-run `performance.now()` wall-clock observations without benchmark warmup or repeated samples; they are not benchmark guarantees.

Three local JSON downloads use `schemaVersion: 1` and an export-time snapshot:

- Full: `schemaVersion`, `generatedAt`, `environment`, `webgpu`, `jpeg`.
- JPEG-only: `schemaVersion`, `generatedAt`, `environment`, `jpeg`.
- WebGPU-only: `schemaVersion`, `generatedAt`, `environment`, `webgpu`.

Explicit report projections omit asset IDs, filenames, thumbnail/original URLs, Immich URLs, hostnames/IPs, EXIF, pixel data, histogram bins, Recipe, History, clipboard, storage contents and credentials. JPEG dependency exceptions are converted to semantic error codes without raw detail because they can contain private IDs or URLs. The page performs no telemetry or report upload; downloads use a local Blob.

#### Lifecycle

Each JPEG run owns its AbortController, object URL and renderer. `pagehide` aborts pending candidate/run work and disposes resources; a persisted BFCache `pageshow` creates a fresh owner. Object URLs are revoked, renderers/devices are disposed, `requestDevice()` or renderer creation that completes after departure releases its late resource, and closed owners cannot publish. Effect cleanup also handles React StrictMode and route unmount. WebGPU Smoke follows the same run-owner and departure rules. These mechanisms keep tab switching from interrupting runs while still cleaning up on page departure.

### Histogram collection and Scope display

collectHistogram() in histogram.ts is a DOM-independent pure function over the decoded RGBA Uint8ClampedArray. It counts the 8-bit sRGB R, G, and B code values directly into 256-bin Uint32Arrays and ignores alpha. Y′ uses the nonlinear code values with 0.2126R′ + 0.7152G′ + 0.0722B′, rounded with Math.round and clamped to bins 0–255. The function does not alter its input, and each channel's bin total equals the number of pixels.

After a source decodes successfully, AdjustedImage computes its Before histogram once and retains it with that decoded source. After the existing renderAdjustments() produces an adjusted buffer, the Worker computes the After histogram from that buffer and returns it alongside the transferable pixel buffer. The main-thread fallback renders once and calls the same collector on its output. No histogram path reads pixels back from Canvas or reruns the image pipeline.

AdjustmentWorkerClient accepts results only when requestId and assetGeneration match the in-flight request. If a newer recipe is pending, it discards the completed result and sends the latest recipe. AdjustedImage reports an adjusted histogram only after the matching pixel result is accepted by the After Canvas. It carries a sourceKey; AnshitsuPage stores the pair with its assetId, rejects callbacks that do not match the current asset and source, and exposes data only when both identities match. The before and after values are independently nullable. null means that result has not been collected; it is not a zero-filled distribution.

The Viewer reports its effective display state (persistent Before OR held Backslash) to AnshitsuPage, which selects the matching histogram without substituting the other one when it is unavailable. Comparison changes only the displayed data and does not cause another render or collection. ScopePanel owns the non-persistent RGB selection, Y Only state, and Normal / Expanded scale state; these remain in place when the active photo changes. At least one RGB channel remains selected. Normal mode uses the maximum bin across all three RGB channels as a shared scale, regardless of individual visibility. Expanded mode computes nearest-rank P99 over all 768 RGB bins, or the 256 Y′ bins in Y Only. Zero bins participate; the ceiling is at least one. Values above it are clipped to the SVG plot edge without changing histogram data. The responsive graph uses the available Scope region, with the existing compact-layout size override.

Scope shortcuts use KeyboardEvent.code: Numpad 0 toggles Y Only, Numpad 1–3 toggle R/G/B, and Numpad Decimal toggles the scale. While Y Only is active, Numpad 1–3 first restore the previous RGB view without toggling its channel. Scope ignores processed or composing events, modifier combinations, native editing targets, blocked workspace actions, and open menus or dialogs. AdjustmentSlider also excludes these five physical keypad codes from its global arrow-key handler because NumLock-off Numpad keys can report arrow names; native text and number inputs are checked first and retain their browser input behavior.

### Edit-status lookup and UI state

`POST /assets/edit-status` accepts at most 100 distinct asset IDs and returns their persisted edited state in one request. The browser distinguishes a missing/unloaded result from confirmed unedited and edited states; a failed or invalid response is not treated as `false`. Home uses the batch result for its grid markers. Filmstrip indicators prefer validated per-asset session state from edit-state GETs or confirmed saves over the older batch baseline. After discarding local edits, a previously confirmed saved state remains known; when that state is uncertain, the stale batch result is invalidated and a fresh status lookup is used rather than presenting it as confirmed.

Home cards and Filmstrip use proxied thumbnails. Home Shift+click selects the inclusive range in visible photo order while preserving existing selection order; Home passes the ordered selection to Anshitsu. A shared `HomeTitle` keeps the title route consistent: on Home it is inert, and in Anshitsu it invokes the existing save-and-exit flow. Connection details open from the Home connection status and close on outside pointer action or Escape. Anshitsu keeps History/EXIF and Scope/Develop panels independently collapsible, with focus navigation following visible controls. Category, adjustment, and 3WAY range context menus share the same edit operations. The Viewer `⋯` menu isolates its key events from workspace shortcuts, then restores focus to its trigger on Escape; real pointer movement from a focused 3WAY heading to a slider clears the stale heading focus so DOM focus and the shared adjustment target stay aligned. Standalone Filmstrip ArrowLeft / ArrowRight navigation was removed; Primary+Shift+ArrowLeft / ArrowRight are the registered commands for adjacent asset movement.

### Save outcomes and edit indicators

When PUT may have committed but its result is unknown (including HTTP 408 or 5xx and an unreadable or invalid success response), the frontend retains and retries the identical snapshot, expected revision, and save ID before attempting later edits. A confirmed retry advances the revision and allows newer edits to save. A genuine 409 remains a conflict and is not automatically merged. After a failed-save discard, the UI keeps confirmed persisted edit status when known; if persistence cannot be determined, it invalidates the earlier batch result and treats the marker as unknown until refreshed. Browser Back, reload, and tab close still have no forced-save interception.

## Future direction (not implemented)

The current authenticated read path is:

```text
Browser → Frontend → Backend API → Immich API
```

Possible extensions include:

- Expanded Immich asset browsing; connection credentials currently come only from backend environment variables.

## Portability and validation

The Windows workspace is only a development directory. Application code and deployment files must not depend on its absolute path or Windows-specific runtime behavior. Deployment must not modify Docker host OS settings or install application files into host system directories. Persistent data uses the explicitly declared `/data` bind mount.

The validation workflow is to develop locally, copy or deploy the required files to the target Docker host, start them with Docker Compose (or Portainer when used), and verify actual behavior there. Successful Windows checks alone do not constitute completed runtime validation.

The deployment runtime check is to open the Web UI, confirm `Backend: Connected`, `Immich: Connected`, and up to 100 recent thumbnails, obtain `{"status":"ok"}` from `/api/health`, and obtain a connected result from `/api/immich/status`. Also verify the empty and failed photo-list states, missing Immich settings, rejected credentials, and the backend stopped. Container builds, nginx routing, real Immich photo and thumbnail access, and restart behavior still require target-environment validation; static checks alone cannot establish them.
